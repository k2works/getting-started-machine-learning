# 第 4 章: ライブラリのエコシステムの比較

## 4.1 突き合わせの目的

各言語版の第 3〜14 章では、アルゴリズムを TDD で自作したあと、その言語の機械学習ライブラリに同じデータを渡して結果を突き合わせました。目的は 2 つです。

- **自作が正しいことの裏付け**: 仕組みの違う実装どうしで結果が一致すれば、自作が妥当に動いていると言える
- **ライブラリの振る舞いを知る**: 既定値や定義の違いは、ドキュメントを読むだけでは見落とす。学習用テストで確かめてから使う

ライブラリの選定の理由は、各言語の ADR にあります（[001 Python](../../../adr/001-python-ml-libraries.md)・[002 Kotlin](../../../adr/002-kotlin-ml-libraries.md)・[003 TypeScript](../../../adr/003-typescript-ml-libraries.md)・[004 F#](../../../adr/004-fsharp-ml-libraries.md)・[005 Java](../../../adr/005-java-ml-libraries.md)・[006 C#](../../../adr/006-csharp-ml-libraries.md)・[007 Scala](../../../adr/007-scala-ml-libraries.md)・[008 Go](../../../adr/008-go-ml-libraries.md)・[009 Rust](../../../adr/009-rust-ml-libraries.md)・[010 Ruby](../../../adr/010-ruby-ml-libraries.md)・[011 Clojure](../../../adr/011-clojure-ml-libraries.md)・[012 Elixir](../../../adr/012-elixir-ml-libraries.md)・[013 PHP](../../../adr/013-php-ml-libraries.md)・[014 Haskell](../../../adr/014-haskell-ml-libraries.md)）。本章の結果も、各 ADR と各言語版の記事から取っています。

## 4.2 章ごとの突き合わせの結果

記号は次の意味です。

- **一致**: 同じ入力で、予測・係数・指標などが一致した（浮動小数点の桁の範囲で）
- **近似**: 一致させるために換算や条件の調整が要った、または一部が一致しなかった
- **比較**: 仕組みや乱数が違うので一致は求めず、正解率や SSE を比べた
- **省略**: 置き換え先が無い・使えないので、自作を最終実装にした

Python は、scikit-learn がほぼすべての章に突き合わせ先を持ち、多くの章で一致しました。ほかの言語は、「手法が無い」「初期中心を渡せない」「定義の尺度が違う」ために、換算や比較にとどめた章があります。それでも、**第 7 章（線形回帰）は 14 言語すべてで一致し、第 11 章（評価指標）は突き合わせ先のある 13 言語すべてで一致しました**。

**置き換えの範囲は、言語によって大きく違います。** 第 3 波でその幅が最も広がりました。

| 置き換えの範囲 | 言語 | 突き合わせられない主な章 |
|--------------|------|----------------------|
| ほぼ全章 | Python・Rust・**PHP** | — |
| 多くの章 | Kotlin・Java・Scala・Clojure・C#・F#・TypeScript・**Ruby** | 13（Tribuo に PCA が無い）など |
| 狭い | **Elixir** | 3・8 の一部・10 の森・12 のラッソ・14（**決定木も森もラッソも無い**） |
| 線形代数だけ | **Haskell** | 3・8・10・11・14（**機械学習のライブラリが無い**） |
| 数値計算のみ | Go | 3・8・10・12・14（gonum は数値計算のライブラリで、機械学習のライブラリではない） |

**第 3 波は、この軸で 2 つの版が正面から対照をなしました。** PHP の Rubix ML は決定木もランダムフォレストも持ち、第 3 章から第 14 章まで突き合わせられます。Elixir の Scholar は**本書の背骨である決定木が丸ごと無く**、第 3 章の時点で「自作がそのまま最終実装」になりました。Ruby（Rumale）と Clojure（Tribuo）はその中間です。

そして **Haskell が最も極端でした。** 機械学習のライブラリが無く（`hlearn` は保守が止まっています）、突き合わせられるのは線形代数の層（hmatrix）と統計（statistics）だけです。その結果、**第 11 章は「突き合わせの節が存在しない」シリーズ唯一の章**になりました。代わりに「値の分かっている入力」（AUC の 1.0 と 0.5、`t=2a` の MSE 0）・「満たすべき性質」（全行をちょうど 1 度テストする、訓練とテストが重ならない）・「ほかの言語版の数値」の 3 つで正しさを支えています。

## 4.3 「ライブラリにある」と「そのまま比べられる」は別

第 3 波で新しく出てきた論点です。ライブラリに手法があっても、**自作と同じ条件に設定できるとは限りません**。

PHP の `Rubix\ML\Classifiers\ClassificationTree` は決定木を持っています。しかし既定のままでは、次の理由で自作と比べられませんでした。

- `CART::split()` が使う列を `array_rand` で毎回選ぶ（`maxFeatures` の既定は `round(sqrt(n))`）
- 連続値の候補を分位点で丸める（`maxBins` の既定は `1 + round(log2(m))`）
- 葉の大きさと不純度の下限に既定値がある

`maxLeafSize: 1`・`minPurityIncrease: 0.0`・`maxFeatures: 列数`・`maxBins: 大きい値` の 4 つを明示して初めて、深さ 1〜5 で完全に一致しました。**Elixir 版がこの章で「突き合わせる相手がいない」という仕事をしたところで、PHP 版には「相手はいるが、そろえる」という別の仕事が現れた**ということです。

同じことが Ruby でも起きました。`Rumale::LinearModel::LinearRegression` は、`Numo::Linalg` が読み込まれていないと L-BFGS（`tol` の既定は 1e-4）で解き、**`solver: "svd"` を指定しても黙って L-BFGS に落ちます**。既定のままでは切片が 0.0044（自作は 6035.99）、テストの決定係数が −1.246 になり、例外も警告も出ません。`tol: 1e-10` にして初めて、自作との差が 3.5e-5 以内になります。

そろえきれない場合もあります。PHP 版で、深さを制限しないときだけ 0.9333 対 0.9111 と食い違った原因は**境界の取り方**でした——自作は隣り合う値の中点、Rubix ML はデータに実在する値を使います。これは引数で変えられません。

## 4.4 学習用テストで見つかったライブラリの癖

突き合わせの前に書いた学習用テストは、ライブラリの思わぬ振る舞いを数多く見つけました。種類ごとに整理します。

### 既定値が「何もしない」ではない

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|
| Python | scikit-learn の `LogisticRegression` | 既定で L2 正則化（`C=1.0`）を掛ける。自作と比べるには `C=np.inf` にする |
| Kotlin・Java・Scala・Clojure | Tribuo の `LogisticRegressionTrainer` | 既定（AdaGrad・5 エポック）では学習が足りない。500 エポックで自作と同じ正解率 |
| Kotlin | Tribuo の `RandomForestTrainer` | `minChildWeight` の既定値 5 では訓練データを分け切らない |
| TypeScript | ml-cart | README に無い `gainThreshold: 0.01` が既定に含まれ、利得の小さい分割をしない |
| TypeScript | ml-regression-lasso | 既定の反復回数では収束しないまま、例外にならずに係数を返す |
| F# | ML.NET の FastTree | 葉ごとの最小件数の既定値が 10 で、小さなテストデータでは分けられない |
| F# | ML.NET の `NormalizeMeanVariance` | 既定（`fixZero`）では平均を引かない |
| Rust | linfa-trees の `DecisionTree` | 既定で `min_impurity_decrease: 1e-5` の事前枝刈りが効く。**0 を渡すと `ParamGuard` が `Err` を返すので、枝刈りを完全に切れない** |
| Rust | linfa-logistic の `MultiLogisticRegression` | 既定で L2 の強さ `alpha` が 1.0。1e-8 に下げると自作（正則化なし）と 45 件すべて一致した |
| **Ruby** | Rumale の `LinearRegression`・`Ridge`・`PCA` | **既定の解き方が黙って落ちる。** `solver: "svd"` を渡しても L-BFGS で解き、PCA の `solver: "evd"` は警告 1 行で固定小数点法に落ちる |
| **Ruby** | Rumale の `LogisticRegression` | 既定は `reg_param: 1.0`・`tol: 1e-4` で、**切片まで正則化する** |
| **Elixir** | Scholar の `LogisticRegression` | 既定の `alpha: 1.0`（L2）が 105 件のデータに強すぎる（訓練 0.6571）。`alpha: 0.0` で自作と完全一致 |
| **Elixir** | Nx | **`Nx.tensor([1.0])` の既定の型が f32。** `type: :f64` を明示しないと重回帰の係数が `0.9999998807907104` になる |
| **PHP** | Rubix ML の `Ridge` | **`l2Penalty` の既定が 1.0。** 省くと最小二乗ではなく別のモデルになる |
| **PHP** | Rubix ML の `LogisticRegression` | 既定の学習率 0.01 では訓練 0.6762（自作 0.9143）。1.0 にすると 0.9333。**正則化（`l2Penalty` の既定 1e-4）はここでは効いていない**——Scholar の `alpha: 1.0` より 4 桁小さい |

**Elixir の f32 は、この表の中でいちばん見つけにくい種類でした。** 丸めた表示では気づけません（切片が f64 `6114.595505694404`、f32 `6114.59716796875` で、どちらも `6114.60` と表示されます）。

### 定義や尺度が違う

標準偏差を「件数で割るか、件数 − 1 で割るか」は、シリーズ全体でいちばん多く踏んだ落とし穴です。**縦持ちで整理します。**

| 割り方 | ライブラリ |
|-------|-----------|
| **n（母標準偏差）** | scikit-learn の `StandardScaler`、linfa-preprocessing の `LinearScaler::standard()`、**Scholar の `StandardScaler`**、**Rubix ML の `ZScaleStandardizer`**、**statistics の `variance`** |
| **n−1（標本標準偏差）** | pandas の `std()`、Tribuo の `MeanStdDevTransformation`（Kotlin・Java・Scala・Clojure）、ml-matrix の `standardDeviation`、gonum の `stat.StdDev`、**Rumale の `StandardScaler`**、**statistics の `stdDev`** |

- **Haskell の statistics は、1 つのライブラリの中で両方を持っています。** `variance` は n で割る最尤推定、`stdDev` は n−1 で割る標本標準偏差の平方根です。**名前から定義を推測すると間違えます。** Haskell 版は `sqrt . variance` が自作と浮動小数点数として完全に一致することと、`stdDev` とは一致しないことを、両方テストに残しました
- **Ruby の Rumale だけが、第 3 波で n−1 側でした。** Scholar・Rubix ML は n 側なので、同じ第 3 波の中で分かれています。ライブラリの癖は言語の性質ではないことが、ここでも出ています

罰則と指標の定義も、ライブラリごとに違いました。

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|

| TypeScript | ml-regression-lasso | 特徴量と正解の両方を標準化した尺度の罰則 |

| 余りの扱い | ライブラリ |

Scholar と Rubix ML は、891 件を 5 分割すると 178 件 × 5 になり、**1 件がどの分割でもテストされません**。別々に書かれた 2 つのライブラリが、まったく同じ振る舞いをしていました。自作は 179, 178, 178, 178, 178 で全行をちょうど 1 度テストします。

**Ruby は逆に、行の分け方まで一致しました。** Rumale の `KFold` の `shuffle: true` は、第 2 章の `shuffle` と同じ `Random.new(seed)` と `Array#shuffle` を使うので、891 件の 5 分割が行単位で自作と一致します。

### 決定的でない

**第 3 波で、この節がいちばん大きくなりました。** 「同じ入力に同じ出力」が成り立たないライブラリは、linfa-trees だけではありませんでした。

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|

第 2 波で「自作のほうが再現性が高いという逆転」が linfa で起きたことを書きました。**第 3 波では、それが例外ではないと分かりました。** ライブラリは「自分で書くより正しい」とは限らず、「自分で書くより再現する」とも限りません。

## 4.5 C ライブラリへの依存——確認すべきことが 3 段ある

**第 3 波の Haskell で初めて出てきた論点です。** ネイティブのライブラリに依存すると、「入るかどうか」だけでは足りません。

hmatrix は BLAS/LAPACK を要求します。確認は 3 段ありました。

1. **ビルドが通るか。** 素の Nix 環境では `configure` が `Missing (or bad) C libraries: blas, lapack` で止まります。**ここを通っただけで採用を決めたのが、最初の誤りでした**
2. **呼び出しが通るか。** nixpkgs の `openblas` は既定が `blas64 = true`（ILP64。整数引数が 64 ビット）で、**32 ビット整数で呼ぶ hmatrix と ABI が噛み合いません。** ビルドは成功するのに、**2×2 の連立方程式すら解けませんでした**（`linearSolve` が `Nothing` を返し、`<\>` は `code -7`、`pinv` は `code -2`）。`blas` と `lapack`（`isILP64 = false`）に差し替えて解決しています。**2×2 の `DGESV` で「行列の次数が不正」と言われたら、数値の問題ではなく ABI の不一致を疑う**、という診断がここで得られました
3. **環境を変えたあと作り直されるか。** 環境定義を直しても、cabal の store に残った成果物は作り直されません。**`LIBRARY_PATH` は環境ごとに変わるのに、cabal はそれをパッケージのハッシュに含めない**ので、ILP64 の BLAS にリンク済みのものが使われ続けます。store の該当エントリを退避してから作り直す必要がありました

Elixir 版が EXLA（巨大な XLA のバイナリ）を避けたのとは、判断が逆になっています。BLAS/LAPACK は数値計算の標準的な土台で Nix でも軽く入るため、依存を受け入れました。その代わりに、**「ライブラリがビルドできた」は「使える」ではない**という確認の段が 2 つ増えています。

似た形は第 3 波でもう 2 回起きました。**PHP の素の Nix 環境にはカバレッジドライバ（xdebug も pcov も）が無く**、`php.withExtensions` で pcov を足す必要がありました。**Clojure の環境には clj-kondo も cljfmt も入っておらず**、Haskell の環境には fourmolu も hlint もありませんでした。**道具立てが環境に足りないことは、第 3 波では例外ではなく既定でした。**

## 4.6 同じ計算を違う入れ物で渡すと、精度が変わる

第 7 章の線形回帰で、**3 つの版が「SVD で解いた」と言いながら 3 通りの結果になりました。**

| 版 | ライブラリ | 解き方 | 結果 |
|----|-----------|-------|------|
| **Elixir** | Scholar の `LinearRegression` | `Nx.LinAlg.pinv`（SVD） | **最小二乗解に届かない。** 特異値 `[12988, 2648, 1589, 4.28]` のデータで、残差平方和が自作 11083165.68 < Scholar 14073810.01。列を標準化してから渡すと有効数字 4 桁までそろう |
| **PHP** | Rubix ML の `Ridge` | **正規方程式**を `inverse()` で解く（自作は LU 分解） | **12〜13 桁まで一致した**（切片 6114.5955056944 対 6114.5955056945） |
| **Haskell** | hmatrix の `<\>`（DGELSS） | 計画行列を渡すと SVD、正規方程式を渡しても同じ関数 | **計画行列なら 12 桁、正規方程式なら 9 桁**（6114.5955055106010） |

**Haskell 版は、この対照を 1 つのライブラリの中で見せました。** 同じ実データを 4 通り（自作のガウス・ジョルダン法／`<\>` に計画行列／`linearSolveLS` に計画行列／`<\>` に正規方程式）で解くと、最初の 3 つは 12 桁まで一致し、最後だけが 9 桁に落ちます。`XᵀX` を作ると条件数が 2 乗になるという教科書どおりのことが、**同じ関数に別の入れ物で渡しただけ**で出ました。

面白いのは、**自作も正規方程式を解いているのに 12 桁一致している**ことです。違いは部分ピボット選択つきの消去法と DGELSS（特異値の打ち切りあり）で、残差平方和は 4 つとも下 2 桁しか違いません。**どれも最小二乗解の底にはいて、底が平らなので係数のほうが先にぶれる**、というのが答えでした。

Elixir 版が「SVD のほうが数値的に安定である」という一般論に裏切られ、PHP 版が「正規方程式は条件数が悪くなる」という一般論に裏切られています。**アルゴリズムの理論的な安定性より、その実装の精度のほうが効く場合がある**ということです。

## 4.7 ライブラリが無いことが、安全な設計を強制した例

第 3 波では、モデルの保存・復元でも版ごとに事情が分かれました。

| 版 | 保存の方法 | 用心 |
|----|----------|------|
| Ruby | `Marshal` | RuboCop の `Security/MarshalLoad` を理由つきで 1 行だけ無効にした |
| Clojure | EDN（`pr-str`／`read-string`） | 学習済みパイプラインがマップ・ベクタ・キーワードだけなので、値として `=` で比べられる |
| Elixir | `:erlang.term_to_binary` | 復元には `:safe` を渡す |
| PHP | `serialize` | **`unserialize()` に `allowed_classes` は必須**（既定でどんなクラスでも作る）。しかも `unserialize()` も `mkdir()` も失敗を例外ではなく警告で知らせる |
| Haskell | `Data.Binary` | **用心が要らなかった** |

**Haskell で用心が要らなかったのは、ライブラリが足りなかったからです。** `binary` に `Text` の `Binary` インスタンスが無く、孤児インスタンスを避けて保存の形式を手書きすることになりました。その結果、**「壊れたファイルから任意のものが作られない」という性質が設計に組み込まれました**。PHP の `allowed_classes`・Elixir の `:safe` にあたる用心が、そもそも要らなくなっています。

（ただし別の注意は増えました。`decodeOrFail` は「途中まで読めたら成功」なので、余りが空かまで見る必要があります。）

**往復の精度も分かれました。** Clojure の EDN と Elixir の `:erlang.term_to_binary` は `Double` を往復しても桁が落ちず、PHP の `serialize` も `serialize_precision` の既定 `-1` が最短往復表記を選ぶので、実データでも 1 ビット一致します。

## 4.8 エコシステムの成熟度と、自作の意味

14 言語を比べると、ライブラリが成熟しているほど「一致」が増え、成熟していないほど「近似」「比較」「省略」が増えました。

| Kotlin・Java・Scala・Clojure | 第 7・11 章 | 同数・境界の扱い、不偏標準偏差、罰則の尺度、手法が無い（PCA）、初期中心を渡せない（いずれも Tribuo の性質） |

| **PHP** | 第 7・9・12・13 章 | 既定値をそろえる手間、F 値の定義、ROC が無い、**シードを渡す口が無い** |
| **Haskell** | 第 7・9・12・13 章 | **機械学習のライブラリが無く、線形代数と統計だけが相手** |

**同じライブラリを使う言語は、同じ結果になりました。** Java・Scala・Kotlin・Clojure（Tribuo）と C#・F#（ML.NET）は、突き合わせの結果も見つかった癖もほぼ同じです。第 3 波で Clojure が同じ Tribuo 4.3.2 を同じ JDK 21 で呼んだ結果、**自作と CART の相違件数（深さ 1〜10 で 0,0,0,0,2,0,0,0,1,0）まで Java 版・Scala 版と一致しました**。ライブラリの癖は言語の性質ではなく、ライブラリの性質だということが、4 言語で確かめられたことになります。

ただし、「一致しない」ことは失敗ではありません。一致しなかった原因を学習用テストで突き止めたことで、ライブラリの定義（同数の扱い・罰則の尺度・F 値の平均の取り方）を正確に理解できました。ライブラリが無い部分は、自作が最終実装になります。

**そして、ライブラリが無い版でも正しさは支えられました。** Haskell 版の第 11 章は、突き合わせる相手が 1 つも無い状態で、「値の分かっている入力」「満たすべき性質」「ほかの言語版の数値」の 3 つで正しさを示しています。**ほかの言語版の数値が突き合わせの相手になる**のは、14 言語で同じ題材を書いたシリーズならではの支え方です。第 3 波の 3 言語（Elixir・PHP・Haskell）が乱数生成器を自作して JVM の言語版と並びをそろえたのは、まさにこのためでした。

## 4.9 まとめ

1. **章ごとの突き合わせ** — 第 7 章（線形回帰）は 14 言語すべてで、第 11 章（評価指標）は相手のいる 13 言語すべてで一致した。ほかの章は、ライブラリの成熟度によって一致・近似・比較・省略に分かれた
2. **置き換えの範囲は言語で大きく違う** — PHP（Rubix ML）はほぼ全章、Elixir（Scholar）は決定木が無いので狭く、**Haskell は機械学習のライブラリが無く線形代数だけ**。第 11 章は「突き合わせの節が存在しない」シリーズ唯一の章になった
3. **「ある」と「そのまま比べられる」は別** — Rubix ML の決定木は 4 つの引数を明示して初めて比べられ、Rumale の線形回帰は `tol` を下げるまで切片が 0.0044 だった。**相手がいることは、そろえる仕事が要ることでもある**
4. **既定値を疑う** — 正則化・エポック数・学習率・葉の最小件数・`fixZero`・`min_impurity_decrease`・**Nx の f32**・**`Ridge` の `l2Penalty`** など、「何もしない」と思った既定値が結果を変えた
5. **定義をそろえる** — 標準偏差の割り方は 11 のライブラリで割れた。**statistics のように 1 つのライブラリが両方を持つ**こともあり、名前から推測すると間違える。K 分割の余りは「配る／捨てる」で分かれ、Scholar と Rubix ML が同じ「捨てる」だった
6. **決定的とは限らない** — linfa-trees・Rubix ML の 3 つのクラス・Rumale のモデル・Scholar の KMeans が、種を渡さないと揺れた。**シードを渡す口が無い**場合は、くじ引きを起こさない設定にするか、大域に種を付けるしかない
7. **C ライブラリへの依存は 3 段で確認する** — ビルドが通るか、呼び出しが通るか（ABI の整数幅）、環境を変えたあと作り直されるか。**ビルドが通っただけでは使えない**
8. **同じ計算でも入れ物で精度が変わる** — 「SVD で解いた」が 3 つの版で 3 通りになった。アルゴリズムの理論的な安定性より、その実装の精度のほうが効く場合がある
9. **癖はライブラリの性質** — 同じ Tribuo を使う 4 言語（Java・Kotlin・Scala・Clojure）は、相違件数まで同じだった
10. **一致しないことも学び** — 原因を学習用テストで突き止め、ライブラリの定義を理解した。手法が無い部分は自作を最終実装にし、**ほかの言語版の数値を突き合わせの相手にした**
