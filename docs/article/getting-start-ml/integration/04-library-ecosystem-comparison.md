# 第 4 章: ライブラリのエコシステムの比較

## 4.1 突き合わせの目的

各言語版の第 3〜14 章では、アルゴリズムを TDD で自作したあと、その言語の機械学習ライブラリに同じデータを渡して結果を突き合わせました。目的は 2 つです。

- **自作が正しいことの裏付け**: 仕組みの違う実装どうしで結果が一致すれば、自作が妥当に動いていると言える
- **ライブラリの振る舞いを知る**: 既定値や定義の違いは、ドキュメントを読むだけでは見落とす。学習用テストで確かめてから使う

ライブラリの選定の理由は、各言語の ADR（[001 Python](../../../adr/001-python-ml-libraries.md)・[002 Kotlin](../../../adr/002-kotlin-ml-libraries.md)・[003 TypeScript](../../../adr/003-typescript-ml-libraries.md)・[004 F#](../../../adr/004-fsharp-ml-libraries.md)・[005 Java](../../../adr/005-java-ml-libraries.md)・[006 C#](../../../adr/006-csharp-ml-libraries.md)・[007 Scala](../../../adr/007-scala-ml-libraries.md)・[008 Go](../../../adr/008-go-ml-libraries.md)・[009 Rust](../../../adr/009-rust-ml-libraries.md)）にあります。本章の結果も、各 ADR と各言語版の記事から取っています。

## 4.2 章ごとの突き合わせの結果

記号は次の意味です。

- **一致**: 同じ入力で、予測・係数・指標などが一致した（浮動小数点の桁の範囲で）
- **近似**: 一致させるために換算や条件の調整が要った、または一部が一致しなかった
- **比較**: 仕組みや乱数が違うので一致は求めず、正解率や SSE を比べた
- **省略**: 置き換え先が無い・使えないので、自作を最終実装にした

**第 1 波**

| 章 | Python（scikit-learn） | Kotlin（Tribuo） | TypeScript（ml.js 系） | F#（ML.NET・FSharp.Stats） |
|----|----------------------|-----------------|---------------------|--------------------------|
| 3 決定木 | 一致（深さ 4 通りで 45 件すべて） | 近似（深さ 2 まで一致、3 以上で 1 件違う） | 近似（深さ 3 だけ 1 件違う） | 近似（単一の決定木が無く、1 本だけの FastTree で代用。深さ 2 で 45 件すべて一致） |
| 7 線形回帰 | 一致（評価指標） | 一致（`SLMTrainer(true)`・`LARSTrainer` で予測が小数第 13 位まで） | 一致（係数・予測が小数第 9 位まで） | 一致（FSharp.Stats の `LinearRegression.fit`、小数第 9 位まで） |
| 8 前処理パイプライン | scikit-learn の `Pipeline` そのものを実装に使った | 近似（深さ 1〜6 は一致、7〜10 で 1〜7 件違う。クラスの重みは自作） | 近似（深さ 1〜6 は 179 件一致、7〜10 で違う。クラスの重みは自作） | 近似（ML.NET の行の重みでクラスの重みを表せた） |
| 9 標準化 | 一致（`ddof=0` にそろえる） | 近似（不偏標準偏差なので √((n−1)/n) を掛ける） | 省略（標準化のライブラリを採用せず自作を最終実装に） | 一致（`fixZero = false` にそろえる） |
| 10 ロジスティック回帰・ランダムフォレスト | ロジスティック回帰は一致（正則化なしにそろえる）、森は比較 | 比較（500 エポックで自作と同じ正解率） | 比較（ml-logistic-regression に切片が無い） | 比較 |
| 11 評価指標・交差検証 | 一致（同じ分割を渡すと交差検証の平均も一致） | 一致（`LabelEvaluator`・`KFoldSplitter`） | 一致（ml-confusion-matrix）。交差検証は分け方が違う | 一致（評価指標）。交差検証は分け方を ML.NET が決めるので比べていない |
| 12 リッジ・ラッソ回帰 | 一致（`Ridge`） | 近似（`ElasticNetCDTrainer` の罰則を換算して 1e-6 以内） | 近似（ラッソの `lambda` は標準化した尺度） | 近似（FSharp.Stats のリッジ回帰は使えず、ML.NET の SDCA を換算して小数第 3 位まで） |
| 13 主成分分析 | 一致（符号をそろえる） | 省略（Tribuo に PCA が無い。固有値分解は Tribuo） | 一致（ml-pca、符号をそろえる） | 一致（FSharp.Stats の `PCA.compute`） |
| 14 K-means | 一致（同じ初期中心） | 比較（初期中心を渡せないので SSE） | 一致（同じ初期中心で 100 通りすべて） | 一致（FSharp.Stats、100 通りすべて）。ML.NET とは SSE を比較 |

|----|---------------|-------------|----------------|------------|--------------|

| 12 リッジ・ラッソ回帰 | 近似（罰則を換算） | 近似 | 近似 | **省略**（gonum に無い） | 近似（目的関数の流儀が違う） |
| 13 主成分分析 | 省略（Tribuo に PCA が無い） | 近似 | 省略（同上） | 一致（`stat.PC`、符号をそろえる） | 一致（linfa-reduction、符号をそろえる） |
| 14 K-means | 比較（初期中心を渡せない） | 比較 | 比較 | **省略**（gonum に無い） | 比較（初期中心のシードは渡せるが k-means++ で選び方が違う） |

Python は、scikit-learn がほぼすべての章に突き合わせ先を持ち、多くの章で一致しました。ほかの言語は、「手法が無い」「初期中心を渡せない」「定義の尺度が違う」ために、換算や比較にとどめた章があります。それでも、**第 7 章（線形回帰）と第 11 章（評価指標）は、9 言語すべてで一致しました**。

**第 2 波で両極に分かれたのが Go と Rust です。** Go は 9 言語でいちばん置き換え先が少なく、決定木・ロジスティック回帰・ランダムフォレスト・リッジ／ラッソ・K-means の 5 つの章が「省略」（自作が最終実装）になりました。Rust は逆に、linfa がすべての章に突き合わせ先を持ち、Java 版・C# 版と同じ密度で比べられました。執筆前の見込みでは Rust も Go 側だと考えていたので、ここは実際に書いて初めて分かったことです。

## 4.3 学習用テストで見つかったライブラリの癖

突き合わせの前に書いた学習用テストは、ライブラリの思わぬ振る舞いを数多く見つけました。種類ごとに整理します。

### 既定値が「何もしない」ではない

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|
| Python | scikit-learn の `LogisticRegression` | 既定で L2 正則化（`C=1.0`）を掛ける。自作と比べるには `C=np.inf` にする |
| Kotlin | Tribuo の `LogisticRegressionTrainer` | 既定（AdaGrad・5 エポック）では学習が足りない。500 エポックで自作と同じ正解率 |
| Kotlin | Tribuo の `RandomForestTrainer` | `minChildWeight` の既定値 5 では訓練データを分け切らない |
| TypeScript | ml-cart | README に無い `gainThreshold: 0.01` が既定に含まれ、利得の小さい分割をしない |
| TypeScript | ml-regression-lasso | 既定の反復回数では収束しないまま、例外にならずに係数を返す |
| F# | ML.NET の FastTree | 葉ごとの最小件数の既定値が 10 で、小さなテストデータでは分けられない |
| F# | ML.NET の `NormalizeMeanVariance` | 既定（`fixZero`）では平均を引かない |
| Java・Scala | Tribuo の `LogisticRegressionTrainer` | Kotlin 版と同じく、既定の 5 エポックでは学習が足りない |
| Rust | linfa-trees の `DecisionTree` | 既定で `min_impurity_decrease: 1e-5` の事前枝刈りが効く。**0 を渡すと `ParamGuard` が `Err` を返すので、枝刈りを完全に切れない** |
| Rust | linfa-logistic の `MultiLogisticRegression` | 既定で L2 の強さ `alpha` が 1.0。1e-8 に下げると自作（正則化なし）と 45 件すべて一致した |

### 定義や尺度が違う

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|
| Python | pandas の `std()` | 不偏標準偏差（`ddof=1`）。scikit-learn の `StandardScaler` は件数で割る |
| Kotlin | Tribuo の `MeanStdDevTransformation` | 不偏標準偏差を使う |
| TypeScript | ml-matrix の `scale`・`standardDeviation` | 既定は不偏標準偏差 |
| Kotlin | Tribuo の `ElasticNetCDTrainer` | 罰則は `alpha × l1Ratio × 件数`。`l1Ratio=0` は拒否される |
| TypeScript | ml-regression-lasso | 特徴量と正解の両方を標準化した尺度の罰則 |
| F# | ML.NET の SDCA | L2 の罰則は、自作の `alpha` の `2 / 件数` 倍 |
| F# | FSharp.Stats の `PCA.compute` | `VarianceOfComponent` は、名前に反して分散ではなく標準偏差を返す |
| Go | gonum の `stat.StdDev` | 標本標準偏差（n−1 で割る）。scikit-learn・linfa の標準化（母標準偏差）とは違う |
| Rust | linfa-preprocessing の `LinearScaler::standard()` | **母標準偏差**（n で割る）。scikit-learn と同じで、Tribuo・gonum とは違う |
| Rust | linfa-elasticnet | ラッソの目的関数が「平均で割らない」流儀なので、`alpha` の値をほかの言語版と比べられない |

標準偏差を「件数で割るか、件数 − 1 で割るか」は、Python・Kotlin・TypeScript・Go の 4 言語で同じ落とし穴になりました。逆に Rust の linfa は母標準偏差なので、自作とそのまま一致します。どのライブラリも間違ってはいませんが、既定が違うので、突き合わせるには自作かライブラリのどちらかをそろえる必要があります。

### 並び順・符号・番号が違う

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|
| Python・TypeScript・F# | 主成分分析 | 固有ベクトルの符号に決まりが無い。向きをそろえてから比べた（F# 版は、絶対値が最大の要素を正にそろえた） |
| Kotlin | Tribuo の `eigenDecomposition()` | 対称でない行列では空の `Optional` を返す |
| TypeScript | ml-matrix の `EVD` | 固有値を小さい順に並べる |
| TypeScript | ml-regression-multivariate-linear | 切片が係数の最後に並ぶ |
| F# | FSharp.Stats の K-means | クラスタ番号が 1 から始まる |
| F# | ML.NET の K-means | クラスタ番号が 1 から始まる |
| Go | gonum の `mat.EigenSym` | 固有値を**小さい順**に返し、固有ベクトルは**列**に並ぶ（Tribuo は大きい順） |
| Go | gonum の `stat.PC` と `mat.EigenSym` | 同じデータで第 2 主成分だけ符号が逆向きになった（値は小数第 13 位まで一致） |
| Rust | linfa-trees | 学習は `<= split_value`、予測は `< split_value` で、**境界ちょうどの値の扱いが学習と予測で逆になる** |

### 同数・境界の扱いが違う

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|
| Kotlin | Tribuo の CART | 多数決が同数の葉のラベルの選び方と、同じ不純度の分割候補の選び方が自作と違う |
| TypeScript | ml-cart | 境界ちょうどの値を右に進める。多数決が同数なら訓練データ全体で先に現れたラベルを選ぶ |
| TypeScript | ml-cross-validation | 余りの行が分割数以上だと、行を捨てる |
| TypeScript | ml-confusion-matrix | 正例を一度も予測しないと、適合率が `NaN` になる |
| Rust | linfa-trees の `find_modal_class` | `HashMap` を走査するので、葉のラベルが同数のときの選び方が順に依存しうる |

決定木の予測がライブラリと 1〜2 件だけ違う原因は、多くがこの「同数・境界」でした。Kotlin 版・TypeScript 版・Rust 版は、その原因を学習用テストやライブラリのソースで 1 つずつ突き止めています。

### 決定的でない

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|
| Rust | linfa-trees | **同じデータ・同じ深さでも、実行ごとにテストの正解率が 0.788〜0.810 で揺れる**（第 8 章の `Survived.csv`。ダミー変数で同じ不純度の分割候補が並ぶため。iris では揺れない） |

第 2 波でいちばん意外だったのがこれです。**自作のほうが再現性が高いという逆転**が起きました。出力を固定するテストの対象にできないので、Rust 版の第 8 章は範囲で確かめるテストに変えています。ライブラリは「自分で書くより正しい」とは限りません。

### 使えない・手法が無い

| 言語 | ライブラリ | 見つかったこと |
|------|-----------|--------------|
| Kotlin | Tribuo | PCA のモジュールが無い。K-means は初期中心を渡せない |
| F# | ML.NET | 単一の決定木（CART）の学習器が無い。K-means は初期中心を渡せない |
| F# | FSharp.Stats 0.6.0 | リッジ回帰（`RidgeRegression.fit`）が、どの大きさの罰則の行列でも次元が合わない例外を投げる |
| F# | ML.NET の `Ols` | x64 専用のネイティブライブラリ（Intel MKL）に依存するので採用しなかった |
| TypeScript | ml.js 系 | 回帰の評価指標が無い。`featureImportance()` は型定義に無い |
| Go | gonum | 決定木・ランダムフォレスト・K-means・ロジスティック回帰・正則化付き回帰が無い。`stat.LinearRegression` は単回帰だけ |
| Go | gonum の `stat.ROC` | 入力が昇順でないと `error` ではなく**パニックする**。AUC は返さないので `integrate.Trapezoidal` を別に呼ぶ |
| Rust | linfa | ランダムフォレスト・欠損値の補完・ダミー変数化が無い |
| Rust | ndarray | 連立方程式を解く関数が無い（`ndarray-linalg` は LAPACK を要求する） |

### 言語との橋渡し

| 言語 | 見つかったこと |
|------|--------------|
| TypeScript | 型定義を同梱しないパッケージには、使う範囲だけの型宣言（`declare module`）を自分で書いた |
| TypeScript | `ml-confusion-matrix` の `fromLabels` は、型引数を明示しないとリテラル型に推論される |
| F# | ML.NET は C# 向けの API で、`[<CLIMutable>]` のレコードと `SchemaDefinition` で F# の値を渡した |
| F# | ML.NET の学習器は、F# では共変性を使わないので `:> IEstimator<_>` で明示的にアップキャストした |
| F# | FSharp.Stats の `PCA.compute` は、途中の値を標準出力に書き出す |
| Java | Tribuo に渡すには、特徴量を `ArrayExample` に詰め替え、ラベルを `Label` 型にする |
| Go | gonum の `mat` は自作の行列と違い、行優先のスライスを形で解釈する |
| Rust | linfa に渡すには `Dataset::new(Array2, Array1)` の形にする。決定木はラベルを整数に符号化するが、ロジスティック回帰は `String` のまま渡せる |
| Rust | **クレートの版が型を分ける。** linfa に渡す ndarray は 0.16、RNG は rand 0.8 系でなければ「同じ名前の別の型」としてコンパイルが通らない |

## 4.4 エコシステムの成熟度と、自作の意味

9 言語を比べると、ライブラリが成熟しているほど「一致」が増え、成熟していないほど「近似」「比較」「省略」が増えました。

| 言語 | 一致した章 | 近似・比較・省略の主な理由 |
|------|----------|-----------------------|
| Python | 第 3・7・9・11・12・13・14 章（第 10 章のロジスティック回帰も） | 乱数の使い方が違う（ランダムフォレスト） |
| Kotlin | 第 7・11 章 | 同数・境界の扱い、不偏標準偏差、罰則の尺度、手法が無い（PCA）、初期中心を渡せない |
| TypeScript | 第 7・11・13・14 章 | 同数・境界の扱い、罰則の尺度、切片が無い、標準化のライブラリを採用しない |
| F# | 第 7・9・11・13・14 章 | 単一の決定木が無い、リッジ回帰が使えない、初期中心を渡せない（ML.NET） |
| Java・Scala | 第 7・11 章 | Kotlin 版と同じ（同じ Tribuo を使っている） |
| C# | 第 7・11 章 | F# 版と同じ（同じ ML.NET を使っている） |
| Go | 第 7・11・13 章（いずれも一部） | **手法そのものが無い章が 5 つ**。gonum は数値計算のライブラリで、機械学習のライブラリではない |
| Rust | 第 7・9・10・11・13 章 | 既定の枝刈りと正則化、目的関数の流儀、k-means++、そして**ライブラリ側が非決定的** |

**同じライブラリを使う言語は、同じ結果になりました。** Java・Scala（Tribuo）と C#・F#（ML.NET）は、突き合わせの結果も見つかった癖もほぼ同じです。ライブラリの癖は言語の性質ではなく、ライブラリの性質だということが、2 言語ずつ書いたことではっきりしました。

ただし、「一致しない」ことは失敗ではありません。一致しなかった原因を学習用テストで突き止めたことで、ライブラリの定義（同数の扱い・罰則の尺度）を正確に理解できました。ライブラリが無い部分は、自作が最終実装になります。どの言語でも、まず自作してテストで仕組みを固めておいたことが、ライブラリの癖を見抜く足場になりました。

## 4.5 まとめ

1. **章ごとの突き合わせ** — 第 7 章（線形回帰）と第 11 章（評価指標）は 9 言語すべてで一致した。ほかの章は、ライブラリの成熟度によって一致・近似・比較・省略に分かれた
2. **既定値を疑う** — 正則化・エポック数・利得の下限・葉の最小件数・`fixZero`・`min_impurity_decrease` など、「何もしない」と思った既定値が結果を変えた。linfa のように**既定を切れない**ライブラリもある
3. **定義をそろえる** — 標準偏差の割り方と罰則の尺度は、5 言語以上で同じ落とし穴になった
4. **並び順・符号・同数** — 固有値の順、固有ベクトルの符号、クラスタ番号の始まり、多数決の同数の扱い、**学習と予測で比較演算子が違うこと**は、ライブラリごとに違った
5. **決定的とは限らない** — linfa-trees は同じ入力でも実行ごとに結果が揺れる。自作のほうが再現性が高いという逆転もある
6. **癖はライブラリの性質** — 同じライブラリを使う言語（Java・Scala の Tribuo、C#・F# の ML.NET）は、見つかった癖もほぼ同じだった
7. **一致しないことも学び** — 原因を学習用テストで突き止め、ライブラリの定義を理解した。手法が無い部分は自作を最終実装にした

次の章では、目的に応じた読み方を案内します。
