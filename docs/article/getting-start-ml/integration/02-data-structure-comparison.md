# 第 2 章: データ構造の比較

## 2.1 データの表し方

機械学習のコードの大半は、表形式のデータを読み、列を選び、欠損値を埋め、行を分ける処理です。9 言語は、この表を別々の形で表しました。

| 言語 | 表の表し方 | 1 行の型 | 列の選び方 |
|------|-----------|---------|-----------|
| Python | pandas の `DataFrame` | 無し（列ごとに dtype を持つ） | 列名の文字列（`df["RM"]`） |
| Kotlin | Kotlin DataFrame の `DataFrame` | 無し（列ごとに型を持つ） | 列名の文字列 |
| TypeScript | 型付きレコードの配列（`IrisRow[]`） | `Record<Feature, number \| null>` などのオブジェクトの型 | プロパティ名（列名の和集合の型で検査される） |
| F# | レコードのリスト、特徴量は `Map<string, float>` | 読み込みは型プロバイダの行の型、以降は `Map` | `Map` のキー（列名の文字列） |
| Java | record のリストと `Table`（列の一覧と行） | `Row`（`Map<String, String>` を包む） | 列名の文字列 |
| C# | record のリストと `Table` | `Row`（`IReadOnlyDictionary<string, string>` を包む） | 列名の文字列 |
| Scala | case class と不変のコレクション | `Row`（`Map[String, String]`） | 列名の文字列 |
| Go | 構造体と `map[string]string` | `Row`（非公開の `cells`） | 列名の文字列 |
| Rust | 構造体と `HashMap<String, String>` | `Row`（非公開の `cells`） | 列名の文字列 |

第 2 波の 5 言語は、第 1 波の TypeScript 版・F# 版と同じく**データフレームを使わない**道を採りました。どれも「セルは文字列で持ち、読み出すときに数値へ変換する」形です。CSV のセルは本来ただの文字列で、空欄かどうか・数値として読めるかどうかは読み出す側の関心なので、この形にすると欠損値の扱いを 1 か所にまとめられます。

### データフレームを使った 2 言語

Python と Kotlin は、データフレームのライブラリを使いました。列ごとの集計（平均・欠損値の数）や、列の追加・削除が 1 行で書けるので、第 2 章の前処理は短く書けます。一方で、列の名前は文字列なので、列名の書き間違いは実行するまで分かりません。

### データフレームを使わなかった 7 言語

TypeScript と F#、そして第 2 波の 5 言語は、データフレームを使わずに、言語の型でデータを表しました。

- **TypeScript** は、列名の配列を `as const` で型にし、1 行を `Record<Feature, number | null>` で表しました。存在しない列名を書くと型チェックで誤りになります。ただし、型は実行時に消えるので、CSV の中身が本当にその形かは、読み込みの学習用テストで確かめました（TypeScript 版第 2 章）
- **F#** は、FSharp.Data の **型プロバイダ** で、架空の値のサンプルから CSV の型をコンパイル時に作りました。列名を書き間違えるとコンパイルエラーになります。ただし、特徴量は `Map<string, float>` に移し替えています。欠損値の補完や決定木の分割を「どの列にも同じ処理」として書くには、列を名前で選べる形のほうが扱いやすいためです（F# 版第 2 章）

- **第 2 波の 5 言語** は、`Table`（列の一覧と行）と `Row`（列名からセルの文字列）という同じ形にそろえました。列の選び方は文字列なので、列名の書き間違いは実行するまで分かりません。そのかわり、「どの列にも同じ処理」を書きやすく、第 8 章の前処理パイプライン（欠損値の補完・ダミー変数化）が素直に書けました

TypeScript と F# は、どちらも「読み込みの入り口では型で形を確かめ、その先は汎用の形で扱う」分担になりました。F# では、列の多い CSV（第 9 章の Boston）は型プロバイダではなく、型を持たない `CsvFile` で読んでいます。すべての列を型に書くより、列の一覧を実行時に受け取ってまとめて処理するほうが向いていたためです。

## 2.2 欠損値の表し方

iris の特徴量の 4 列には、合わせて 7 件の空欄があります。9 言語は、空欄を次のように表しました。

| 言語 | 空欄の値 | 補完の後の型 | 補完漏れの見つけ方 |
|------|---------|------------|-----------------|
| Python | `NaN`（pandas が読み込むときに変換） | 同じ（`float64` の列） | テストで欠損値の数を数える |
| Kotlin | `null`（Kotlin DataFrame） | 同じ列の型 | テストで欠損値の数を数える |
| TypeScript | `null`（`number \| null`） | `number`（`Record<K, number>`） | 型チェック（補完前のデータを渡すと誤り） |
| F# | `None`（`float option`） | `float`（`Map<string, float>`） | コンパイル（補完前のデータを渡すと誤り） |
| Java | 空文字列のセル、読み出しは `OptionalDouble` | `Features`（欠損値を持てない） | コンパイル（`Row` を渡すと誤り） |
| C# | 空文字列のセル、読み出しは `double?` | `Features` | コンパイル |
| Scala | 空文字列のセル、読み出しは `Option[Double]` | `Features` | コンパイル |
| Go | 空文字列のセル、読み出しは `(float64, bool, error)` | `Features` | コンパイル（ただし「値と ok」は無視できる） |
| Rust | 空文字列のセル、読み出しは `Result<Option<f64>>` | `Features` | コンパイル |

**「値が無い」をどう表すか**は、言語の道具立てがそのまま出た部分です。`Option` 系（F#・Scala・Rust）と null 許容（Kotlin・TypeScript・C#）と `OptionalDouble`（Java）は同じことを別の形で書いており、Go だけが**多値返却**（値・見つかったか・エラー）になりました。Go 版では 3 つの戻り値のうち「ok」を読み飛ばしてもコンパイルが通るので、型による強制は 9 言語でいちばん弱くなっています。

- TypeScript と F# は、補完の前と後を **別の型** にしました。第 3 章の決定木は補完後の型しか受け取らないので、補完を忘れたデータを渡すと、テストを実行する前に誤りになります
- F# 版の第 2 章では、補完後の「欠損値の数」を表示するために `NaN` の数を数えています。`float` の型には `None` が入らないので、型が欠損値の無いことを保証しているためです
- F# 版では、型プロバイダに推論を任せると、空欄のある列は `string`、小数の列は `decimal` と推論されました。`Schema` で `float option` を指定して、空欄を `None` として読んでいます（F# 版第 2 章）
- F# 版の第 8 章では、乗客のレコードに年齢と乗船港の型を型引数で持たせ（`PassengerOf<'Age, 'Embarked>`）、補完の前（`float option`・`string option`）と後（`float`・`string`）を別の型にしました

欠損値の扱いは、「型で防ぐ」言語と「テストで確かめる」言語に分かれました。第 2 波の 5 言語はすべて前者で、**補完の前（`Row`）と後（`Features`）を別の型にする**という TypeScript 版・F# 版の設計をそのまま引き継いでいます。どちらの場合も、補完に使う平均値は **訓練データだけ** から求める（データリークを防ぐ）という手順は 9 言語で同じです。

## 2.3 分割と乱数

### 同じ手順、違う乱数生成器

9 言語とも、「シードで行の順番を並べ替え、テストデータの件数（割合を掛けて切り上げ）を除いた先頭を訓練データにする」という同じ手順で分けています。違うのは、並べ替えに使う乱数生成器です。

| 言語 | 乱数生成器 | 並べ替え |
|------|-----------|---------|
| Python | NumPy の `np.random.default_rng(seed)` | `permutation` |
| Kotlin | 標準ライブラリの `kotlin.random.Random(seed)` | `shuffled` |
| TypeScript | 自作の mulberry32（`Math.random` はシードを指定できない） | 自作の Fisher–Yates のシャッフル |
| F# | .NET の `System.Random(seed)` | 自作の Fisher–Yates のシャッフル |
| Java | `java.util.Random(seed)` | 自作の Fisher–Yates のシャッフル |
| C# | .NET の `System.Random(seed)` | 自作の Fisher–Yates のシャッフル |
| Scala | `java.util.Random(seed)` | 自作の Fisher–Yates のシャッフル |
| Go | `math/rand` の `rand.New(rand.NewSource(seed))` | 自作の Fisher–Yates のシャッフル |
| Rust | `rand` 0.8 の `StdRng::seed_from_u64(seed)` | 自作の Fisher–Yates のシャッフル |

件数（iris なら訓練データ 105 件・テストデータ 45 件）は 9 言語で一致しますが、**どの行がテストデータに入るか** は一致しません。Python 版の第 2 章では、同じシードでも scikit-learn の `train_test_split` とは分け方が違うことも確かめました。

**同じ乱数生成器を使う言語どうしは一致します。** 0〜9 を同じ Fisher–Yates・同じシード 0 で並べ替えると、次のようになります。

| 乱数生成器 | 言語 | `shuffle(0..10, 0)` |
|-----------|------|---------------------|
| `java.util.Random` | Java・Scala | `[4, 8, 9, 6, 3, 5, 2, 1, 7, 0]` |
| .NET の `System.Random` | C#・F# | （両者で一致。値は各版の第 2 章を参照） |
| Go の `math/rand` | Go | `[6, 8, 2, 3, 7, 5, 9, 1, 0, 4]` |
| Rust の `rand` 0.8 の `StdRng` | Rust | `[9, 3, 6, 4, 8, 1, 5, 2, 0, 7]` |

JVM の 2 言語（Java・Scala）と .NET の 2 言語（C#・F#）は、**言語が違っても実行環境の乱数生成器が同じなので、数値が完全に一致します**。9 言語で 7 通りの結果になりました。「言語ごとに違う」のではなく「**乱数生成器ごとに違う**」というのが正確な言い方です。

### シードだけでは再現できないもの

各版の第 4 章では、シードを固定しても数値が再現できなくなる要因を調べました。

| 言語 | 乱数列が変わりうる要因 | 確かめたこと |
|------|-------------------|------------|
| Python | NumPy の乱数生成器の実装 | 同じシードで同じ並びになることをテストで固定した |
| Kotlin | Kotlin の実行時ライブラリの版 | Kotlin のドキュメントは、同じシードで同じ乱数列になるのは同じ版の Kotlin の間だけだとしている。版をバージョンカタログで固定した |
| TypeScript | 自作の mulberry32 のコード | 32 ビットの整数演算だけで書かれ、結果は ECMAScript の仕様で決まる。参照実装の値をテストで固定した。ただし `Math.exp` などの数学関数は最後の桁まで保証されない |
| F#・C# | .NET の `System.Random` の実装 | シード付きの乱数列が .NET 8.0.22・9.0.11・10.0.1 で同じだったことを学習用テストで確かめた。ただし公式ドキュメントは版をまたいだ一致を約束していない |
| Java・Scala | `java.util.Random` の実装 | `java.util.Random` は、アルゴリズム（線形合同法）が仕様として文書化されている数少ない例。JDK の版が変わっても同じ乱数列になることが約束されている |
| Go | `math/rand` の実装 | ドキュメントに版をまたぐ保証の記述が無い。手元の Go 1.25.5 と 1.26.5 で同じ並びになることを確かめた |
| Rust | `rand` クレートの版 | **`StdRng` のドキュメントは「再現可能と考えるべきではない」と明言している**（実体は ChaCha12。再現が要るなら `rand_chacha` を直接使えとある）。`Cargo.lock` で rand 0.8.8 に固定して再現している |

**再現性の保証は、言語によって 4 段階に分かれました。**

1. **仕様として保証されている** — Java・Scala（`java.util.Random` はアルゴリズムが文書化されている）
2. **自分のコードなので保証できる** — TypeScript（mulberry32 を自作した）
3. **保証は無いが、実測で確かめた** — Python・Kotlin・F#・C#・Go
4. **保証されないと明言されている** — Rust（`Cargo.lock` の固定だけが頼り）

乱数生成器を自作した TypeScript だけが、アルゴリズムをリポジトリのコードとして固定できました。ほかの 8 言語は、言語やランタイムの版を固定し、乱数列が変わればテストが失敗して気付けるようにしています。記事に載せた数値は、どの言語も「シードと版を固定した実装を、実データで動かした結果」です。

## 2.4 表の結合とカテゴリ値

第 9 章では、自転車の利用者数（`bike.tsv`）と天気の対応表（Shift_JIS の `weather.csv`）を結合しました。

| 言語 | 結合 | Shift_JIS の読み込み | 文字コードを指定し忘れたとき |
|------|------|------------------|--------------------------|
| Python | pandas の `merge`（`how="inner"`） | `pd.read_csv(..., encoding="shift_jis")` | `UnicodeDecodeError` で失敗した |
| Kotlin | Kotlin DataFrame の `innerJoin` | `DataFrame.readCSV(..., charset = Charset.forName("Shift_JIS"))` | 例外にならず、文字化けした |
| TypeScript | 天気の番号から名前への `Map` を引く | `TextDecoder("shift_jis")` で文字列にしてから csv-parse に渡す | 例外にならず、文字化けした（U+FFFD） |
| F# | 天気の番号から名前への `Map` を引く | `CodePagesEncodingProvider` を登録してから `StreamReader` で読む | 文字化けすることを学習用テストで確かめた |
| Java・Scala | 対応表を `Map` にして引く | `InputStreamReader` に `Charset.forName("Shift_JIS")` を渡す | 例外にならず、文字化けした |
| C# | 対応表を辞書にして引く | `CodePagesEncodingProvider` を登録してから読む | 例外にならず、文字化けした |
| Go | 対応表を `map` にして引く | `golang.org/x/text/encoding/japanese`（標準ライブラリでは読めない） | **例外にならず、U+FFFD に置き換わる**（デコーダが黙って置換する） |
| Rust | 対応表を `HashMap` にして引く | `encoding_rs` の `SHIFT_JIS.decode` | `String::from_utf8` が `Err` を返す。`decode` は `had_errors` で知らせる |

文字コードの指定を忘れたときの振る舞いは、言語で分かれました。Python（pandas）と Rust（`String::from_utf8`）は失敗として知らせますが、Kotlin・TypeScript・Java・Scala・C#・Go は例外を出さずに文字化けした値を返します。黙って化ける環境では、テストで期待する文字列（「晴れ」）と比べて初めて気付けます。9 言語とも、Shift_JIS で書いた小さなフィクスチャを読むテストで確かめています。

**BOM の扱いも同じ構図です。** 学習データの CSV は BOM 付きなので、素直に読むと先頭の列名が `"\uFEFF身長"` になり、「身長」で引けません。Python は `encoding="utf-8-sig"`、ほかの言語は自分で取り除く処理を書きました。**例外は Rust だけで、csv クレートが BOM を自動で取り除きます**（[ADR 009](../../../adr/009-rust-ml-libraries.md)）。「どの層が面倒を見てくれるか」はライブラリごとに違うので、他人のライブラリの親切に頼るときはテストで確かめてから頼るのが安全です。

天気ごとの平均利用者数（晴れ 4876.8・曇り 4052.7・雨 1803.3）は、分割に関係しないので 9 言語で一致します。データフレームを使わない 7 言語は、どれも「対応表を `Map`（辞書）にして引く」形で結合を書きました。

カテゴリ値（第 8・9 章の性別・乗船港・`CRIME`）は、9 言語ともダミー変数（0 と 1 の列）にしました。ダミー変数化の関数は、機械学習ライブラリに含まれていないことが多く（Tribuo・gonum・linfa にはありません）、ほとんどの言語で自作が最終実装になっています。

## 2.5 まとめ

1. **データフレームか、言語の型か** — データフレームを使ったのは Python と Kotlin だけで、ほかの 7 言語は言語の型（レコード・構造体・`Map`）で列と欠損値を表した。後者は、読み込みの入り口で型で形を確かめ、その先は汎用の形で扱う分担になった
2. **欠損値は型で防ぐか、テストで確かめるか** — TypeScript・F# と第 2 波の 5 言語は補完の前後を別の型にし、補完漏れを型チェック・コンパイルで見つけられるようにした。「値が無い」の表し方は `Option`・null 許容・多値返却に分かれ、Go の多値返却だけは読み飛ばせてしまう
3. **違うのは言語ではなく乱数生成器** — 9 言語で 7 通りの結果になった。JVM の 2 言語（Java・Scala）と .NET の 2 言語（C#・F#）は、言語も書き方も違うのに正解率が 6 行すべて一致する。傾向（過学習）はどの言語でも同じだった
4. **再現性はシードだけでは決まらない** — 保証のされ方は 4 段階に分かれた。仕様として保証されているのは Java・Scala だけで、Rust は「再現可能と考えるべきではない」と明言されている。どの言語も版を固定し、乱数列が変わったらテストで気付けるようにした
