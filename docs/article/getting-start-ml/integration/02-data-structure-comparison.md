# 第 2 章: データ構造の比較

## 2.1 データの表し方

機械学習のコードの大半は、表形式のデータを読み、列を選び、欠損値を埋め、行を分ける処理です。4 言語は、この表を別々の形で表しました。

| 言語 | 表の表し方 | 1 行の型 | 列の選び方 |
|------|-----------|---------|-----------|
| Python | pandas の `DataFrame` | 無し（列ごとに dtype を持つ） | 列名の文字列（`df["RM"]`） |
| Kotlin | Kotlin DataFrame の `DataFrame` | 無し（列ごとに型を持つ） | 列名の文字列 |
| TypeScript | 型付きレコードの配列（`IrisRow[]`） | `Record<Feature, number \| null>` などのオブジェクトの型 | プロパティ名（列名の和集合の型で検査される） |
| F# | レコードのリスト、特徴量は `Map<string, float>` | 読み込みは型プロバイダの行の型、以降は `Map` | `Map` のキー（列名の文字列） |

### データフレームを使った 2 言語

Python と Kotlin は、データフレームのライブラリを使いました。列ごとの集計（平均・欠損値の数）や、列の追加・削除が 1 行で書けるので、第 2 章の前処理は短く書けます。一方で、列の名前は文字列なので、列名の書き間違いは実行するまで分かりません。

### データフレームを使わなかった 2 言語

TypeScript と F# は、データフレームを使わずに、言語の型でデータを表しました。

- **TypeScript** は、列名の配列を `as const` で型にし、1 行を `Record<Feature, number | null>` で表しました。存在しない列名を書くと型チェックで誤りになります。ただし、型は実行時に消えるので、CSV の中身が本当にその形かは、読み込みの学習用テストで確かめました（TypeScript 版第 2 章）
- **F#** は、FSharp.Data の **型プロバイダ** で、架空の値のサンプルから CSV の型をコンパイル時に作りました。列名を書き間違えるとコンパイルエラーになります。ただし、特徴量は `Map<string, float>` に移し替えています。欠損値の補完や決定木の分割を「どの列にも同じ処理」として書くには、列を名前で選べる形のほうが扱いやすいためです（F# 版第 2 章）

TypeScript と F# は、どちらも「読み込みの入り口では型で形を確かめ、その先は汎用の形で扱う」分担になりました。F# では、列の多い CSV（第 9 章の Boston）は型プロバイダではなく、型を持たない `CsvFile` で読んでいます。すべての列を型に書くより、列の一覧を実行時に受け取ってまとめて処理するほうが向いていたためです。

## 2.2 欠損値の表し方

iris の特徴量の 4 列には、合わせて 7 件の空欄があります。4 言語は、空欄を次のように表しました。

| 言語 | 空欄の値 | 補完の後の型 | 補完漏れの見つけ方 |
|------|---------|------------|-----------------|
| Python | `NaN`（pandas が読み込むときに変換） | 同じ（`float64` の列） | テストで欠損値の数を数える |
| Kotlin | `null`（Kotlin DataFrame） | 同じ列の型 | テストで欠損値の数を数える |
| TypeScript | `null`（`number \| null`） | `number`（`Record<K, number>`） | 型チェック（補完前のデータを渡すと誤り） |
| F# | `None`（`float option`） | `float`（`Map<string, float>`） | コンパイル（補完前のデータを渡すと誤り） |

- TypeScript と F# は、補完の前と後を **別の型** にしました。第 3 章の決定木は補完後の型しか受け取らないので、補完を忘れたデータを渡すと、テストを実行する前に誤りになります
- F# 版の第 2 章では、補完後の「欠損値の数」を表示するために `NaN` の数を数えています。`float` の型には `None` が入らないので、型が欠損値の無いことを保証しているためです
- F# 版では、型プロバイダに推論を任せると、空欄のある列は `string`、小数の列は `decimal` と推論されました。`Schema` で `float option` を指定して、空欄を `None` として読んでいます（F# 版第 2 章）
- F# 版の第 8 章では、乗客のレコードに年齢と乗船港の型を型引数で持たせ（`PassengerOf<'Age, 'Embarked>`）、補完の前（`float option`・`string option`）と後（`float`・`string`）を別の型にしました

欠損値の扱いは、「型で防ぐ」言語と「テストで確かめる」言語に分かれました。どちらの場合も、補完に使う平均値は **訓練データだけ** から求める（データリークを防ぐ）という手順は 4 言語で同じです。

## 2.3 分割と乱数

### 同じ手順、違う乱数生成器

4 言語とも、「シードで行の順番を並べ替え、テストデータの件数（割合を掛けて切り上げ）を除いた先頭を訓練データにする」という同じ手順で分けています。違うのは、並べ替えに使う乱数生成器です。

| 言語 | 乱数生成器 | 並べ替え |
|------|-----------|---------|
| Python | NumPy の `np.random.default_rng(seed)` | `permutation` |
| Kotlin | 標準ライブラリの `kotlin.random.Random(seed)` | `shuffled` |
| TypeScript | 自作の mulberry32（`Math.random` はシードを指定できない） | 自作の Fisher–Yates のシャッフル |
| F# | .NET の `System.Random(seed)` | 自作の Fisher–Yates のシャッフル |

件数（iris なら訓練データ 105 件・テストデータ 45 件）は 4 言語で一致しますが、**どの行がテストデータに入るか** は一致しません。Python 版の第 2 章では、同じシードでも scikit-learn の `train_test_split` とは分け方が違うことも確かめました。

### 第 3 章の決定木の正解率

分け方の違いは、そのまま正解率の違いになります。第 3 章の iris の決定木（深さの上限ごと）の正解率を 4 言語で並べます。

| 深さ | Python 訓練 | Python テスト | Kotlin 訓練 | Kotlin テスト | TypeScript 訓練 | TypeScript テスト | F# 訓練 | F# テスト |
|------|-----------|-------------|-----------|-------------|---------------|-----------------|-------|---------|
| 1 | 0.6857 | 0.6222 | 0.6762 | 0.6444 | 0.6952 | 0.6000 | 0.6952 | 0.6000 |
| 2 | 0.9333 | 0.9556 | 0.9429 | 0.9333 | 0.9238 | 0.9778 | 0.9619 | 0.8889 |
| 3 | 0.9619 | 0.9111 | 0.9619 | 0.9333 | 0.9429 | 0.9556 | 0.9714 | 0.8889 |
| 4 | 0.9714 | 0.9111 | 0.9810 | 0.8889 | 0.9524 | 0.9556 | 0.9810 | 0.9111 |
| 5 | 0.9714 | 0.9111 | 0.9810 | 0.8889 | 0.9810 | 0.9111 | 1.0000 | 0.9111 |
| 制限なし | 1.0000 | 0.9111 | 1.0000 | 0.8444 | 1.0000 | 0.9333 | 1.0000 | 0.9111 |

- 深さ 2 のテストデータの正解率は、0.8889（F#）から 0.9778（TypeScript）まで、45 件中 40〜44 件の幅で違います。1 件の違いが 0.0222 の差になるので、1 回の分割の正解率でモデルやアルゴリズムの優劣を決めるのは危険です（各版の第 11 章で交差検証を扱います）
- それでも、読み取れる傾向は 4 言語で同じです。深さを増やすと訓練データの正解率は 1.0 に近づき、テストデータの正解率は頭打ちになります（過学習）
- 深さ 2 の木は、4 言語とも花弁幅だけで 3 品種を分けました。境界の値は、Python が 0.2950、ほかの 3 言語が 0.2750 で、訓練データに入った行の違いがここにも表れています

### シードだけでは再現できないもの

各版の第 4 章では、シードを固定しても数値が再現できなくなる要因を調べました。

| 言語 | 乱数列が変わりうる要因 | 確かめたこと |
|------|-------------------|------------|
| Python | NumPy の乱数生成器の実装 | 同じシードで同じ並びになることをテストで固定した |
| Kotlin | Kotlin の実行時ライブラリの版 | Kotlin のドキュメントは、同じシードで同じ乱数列になるのは同じ版の Kotlin の間だけだとしている。版をバージョンカタログで固定した |
| TypeScript | 自作の mulberry32 のコード | 32 ビットの整数演算だけで書かれ、結果は ECMAScript の仕様で決まる。参照実装の値をテストで固定した。ただし `Math.exp` などの数学関数は最後の桁まで保証されない |
| F# | .NET の `System.Random` の実装 | シード付きの乱数列が .NET 8.0.22・9.0.11・10.0.1 で同じだったことを学習用テストで確かめた。ただし公式ドキュメントは版をまたいだ一致を約束していない |

乱数生成器を自作した TypeScript だけが、アルゴリズムをリポジトリのコードとして固定できました。ほかの 3 言語は、言語やランタイムの版を固定し、乱数列が変わればテストが失敗して気付けるようにしています。記事に載せた数値は、どの言語も「シードと版を固定した実装を、実データで動かした結果」です。

## 2.4 表の結合とカテゴリ値

第 9 章では、自転車の利用者数（`bike.tsv`）と天気の対応表（Shift_JIS の `weather.csv`）を結合しました。

| 言語 | 結合 | Shift_JIS の読み込み | 文字コードを指定し忘れたとき |
|------|------|------------------|--------------------------|
| Python | pandas の `merge`（`how="inner"`） | `pd.read_csv(..., encoding="shift_jis")` | `UnicodeDecodeError` で失敗した |
| Kotlin | Kotlin DataFrame の `innerJoin` | `DataFrame.readCSV(..., charset = Charset.forName("Shift_JIS"))` | 例外にならず、文字化けした |
| TypeScript | 天気の番号から名前への `Map` を引く | `TextDecoder("shift_jis")` で文字列にしてから csv-parse に渡す | 例外にならず、文字化けした（U+FFFD） |
| F# | 天気の番号から名前への `Map` を引く | `CodePagesEncodingProvider` を登録してから `StreamReader` で読む | 文字化けすることを学習用テストで確かめた |

文字コードの指定を忘れたときの振る舞いは、言語で分かれました。Python（pandas）は例外で知らせますが、Kotlin と TypeScript は例外を出さずに文字化けした値を返しました。黙って化ける環境では、テストで期待する文字列（「晴れ」）と比べて初めて気付けます。4 言語とも、Shift_JIS で書いた小さなフィクスチャを読むテストで確かめています。

天気ごとの平均利用者数（晴れ 4876.8・曇り 4052.7・雨 1803.3）は、分割に関係しないので 4 言語で一致します。データフレームを使わない TypeScript と F# は、どちらも「対応表を `Map` にして引く」形で結合を書きました。

カテゴリ値（第 8・9 章の性別・乗船港・`CRIME`）は、4 言語ともダミー変数（0 と 1 の列）にしました。

## 2.5 まとめ

1. **データフレームか、言語の型か** — Python と Kotlin はデータフレームで短く書き、TypeScript と F# は言語の型で列と欠損値を表した。後者は、読み込みの入り口で型で形を確かめ、その先は汎用の形（レコード・`Map`）で扱った
2. **欠損値は型で防ぐか、テストで確かめるか** — TypeScript と F# は補完の前後を別の型にし、補完漏れを型チェック・コンパイルで見つけられるようにした
3. **同じ手順、違う数値** — 4 言語とも同じ手順で分けたが、乱数生成器が違うので正解率は言語ごとに違う。傾向（過学習）は同じだった
4. **再現性はシードだけでは決まらない** — 乱数生成器の実装と版を固定し、乱数列が変わったらテストで気付けるようにした
