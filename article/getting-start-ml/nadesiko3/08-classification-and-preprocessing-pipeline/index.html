            • 8.1 はじめに
            • 8.2 題材とデータ
              • Survived.csv
              • 使う特徴量と、使わない列
              • 年齢はグループごとの中央値で補完する
              • セルは文字列にそろえてから比べる
            • 8.3 TODO リストの作成
            • 8.4 前処理を「種別」を持つ辞書で表す
              • 表は第 2 章と同じ形で、書き換えない
            • 8.5 中央値と、グループごとの補完
              • 中央値
              • グループのキーを JSON にする
              • 知らないグループは全体の中央値で
            • 8.6 乗船した港を最頻値で補完する
            • 8.7 カテゴリ値をダミー変数にする
              • 基準の列を落とす
              • 知らないカテゴリは全部 0
              • 列の順
            • 8.8 クラスの重みを付けた決定木を作る
              • 第 3 章を書き換えずに、重み付きの版を足す
              • 重み付きのジニ不純度
              • balanced の重み
              • 同点のときの決め方
              • 足す順をそろえる
              • 2 億命令の上限に届く
            • 8.9 前処理とモデルをパイプラインにつなぐ
              • 前処理の順番と学習の順番
              • 学習した値を保持して、テストデータに同じ変換を当てる
              • 前処理が済んだ表を特徴量にする
            • 8.10 モデルを保存して読み込む
              • JSON にして 3 行で保存する
              • 読み込んだ JSON の形を確かめる
              • 往復することと、壊れたファイルをテストする
            • 8.11 実データでクラスの重みの効果を確かめる
              • 自作のデータと参照実装で突き合わせる
              • データが無ければ保留にする
              • 効果は深さによって変わる
              • 突き合わせる相手が 1 つも無いとき、何が正しさを支えるのか
            • 8.12 品質チェック
              • 検査に止められたところ

    第 8 章: 実践的な分類と前処理パイプライン¶

    8.1 はじめに¶

    ここまでの章のデータは、比較的きれいでした。アヤメのデータは数値ばかりで、欠損値も数件です。この章では、実務でよく出会う形のデータ を扱います。タイタニック号の乗客データには、文字列の列があり、欠損値が 177 件あり、正解ラベルの偏りがあります。

    この章でやることは 3 つです。

    1. 前処理を部品にして、順に並べる（パイプライン） — 欠損値の補完、カテゴリのダミー変数化。訓練データで学習した値を、テストデータや新しいデータにも同じように当てる
    2. クラスの重みを付ける — 生存者（342 人）より死亡者（549 人）が多いので、素直に学習すると「死亡」に寄る。少数のクラスに重みを付けて、見落としを減らす
    3. 学習済みのパイプラインを保存して読み込む — 学習のたびに計算し直すのではなく、ファイルから読み込んで使う

    なでしこ3 には、機械学習のライブラリも前処理のライブラリもありません（ADR 015）。補完も、ダミー変数化も、決定木も全部自作です。Haskell 版と同じく 突き合わせる相手が 1 つもない章 で、自作の正しさを何で支えるのかが主題になります。

    なでしこ3 版では、次の 4 点に注目してください。

    • 前処理を「種別」を持つ辞書で表す。Haskell 版は前処理の種類を直和型で数え上げ、書き漏らしをコンパイラが止めました。なでしこ3 には型が無いので、前処理["種別"] を見て場合分けし、知らない種別はエラーにして、漏れはテストで捕まえます
    • 保存は JSONエンコード と 保存、読み込みは 開く と JSONデコード。辞書と配列がそのまま JSON になるので保存は 3 行で済みますが、JSONデコード は後ろに続くごみを黙って無視します。読み込んだ JSON の形を自分で確かめます
    • 足す順を変えない。重み付きの不純度は、浮動小数点数を足す順で最後の桁が変わります。Haskell 版と同じ木にするため、足す順まで合わせます
    • gonako には 1 回の実行で 2 億命令という上限がある。最初に書いた素直な実装は、自作のデータのテストで上限に届いて止まりました

    足す順をそろえる¶

    重み付きの不純度には、第 3 章に無かった難しさがあります。重みを付けなければ重みはすべて 1 で、合計は整数なので足す順に関係なく同じ値になります。balanced の重みは 712 ÷ (2 × 件数) のような割り切れない数で、足す順が違うと最後の桁が変わります。

    最後の桁の違いは、ふつうは結果に効きません。効くのは、数学的には同じ不純度になる候補が 2 つ並んだときです。「同じなら先に見つけたほう」の規則が、最後の桁の違いで「小さいほう」に変わり、別の木になります。Haskell 版と同じ木にするには、Haskell 版と同じ順で足す必要があります。Haskell 版の sum は前から順に足すので、なでしこ3 版も前から順に足し、左右の合計もそれぞれの先頭から足し直します。

    参照実装を Python で書くときも同じ注意が要ります。Python 3.12 以降の sum は浮動小数点数を補正しながら足す（Neumaier の方法）ので、前から順に足した値と最後の桁が違うことがあります。参照実装では sum を使わず、ループで前から足しました。

    読み込んだ JSON の形を確かめる¶

    問題は読み込みです。ほかの言語版は「ファイルの中身で任意のものを作らせない」用心をしていました。PHP 版は unserialize() に allowed_classes、Elixir 版は :erlang.binary_to_term に :safe、Clojure 版は clojure.edn/read-string です。

    なでしこ3 の JSONデコード が作るのは辞書・配列・文字列・数値・真偽値・NULL だけなので、任意のものが作られる心配はありません。その代わり、形が違っても何も言わずに読み込みます。木の節に 境界 が無ければ、予測のときに値の無いものとの比較になり、エラーにならずに右の部分木へ進みます（境界の無い節に 0 を渡しても 100 を渡しても、右の葉になりました）。そこで、読み込んだ JSON の形（種別・必要なキー・値の種類）を自分で確かめます。

    自作のデータと参照実装で突き合わせる¶

    学習データはこの環境に無いので、これまでの章と同じく、自作のデータと Python の参照実装で数値を確かめました。参照実装は、Haskell 版と同じ規則（java.util.Random の分割・グループのキー・値の順・同点の扱い・足す順）で書いた使い捨てのスクリプトです。

    自作のデータは 2 つです。

    データ 形 使い方
    20 行の自作データ 実データと同じ 11 列、年齢の空欄 3 件、港の空欄 1 件 テストファイルに直接書き、乗客報告作成 を呼ぶ
    891 行の自作データ 実データと同じ 11 列・BOM 付き、年齢の空欄 177 件・客室の空欄 687 件・港の空欄 2 件・生存 342 人 ML_DATA_DIR で指して実データの分岐を動かす

    どちらも乱数で作った架空の値で、配布データの行は含みません。

    20 行の自作データは、none と balanced で見つけた生存者の数が変わるものを選びました。報告は次のとおりで、なでしこ3 版と参照実装の出力は 1 文字も違いませんでした。これをテストの期待値にしています。

    データ件数: 20（生存 11, 死亡 9）
訓練データ: 16 件, テストデータ: 4 件
classWeight=none: 訓練 1.000, テスト 0.750, 生存者 1 人中 1 人を発見

    891 行の自作データでは、報告の文字列が一致したうえで、保存したモデルの JSON を参照実装のモデルと突き合わせ、学習した中央値・最頻値・列の順と、深さ 5 の木の 51 個の節と葉（境界と不純度を含む）が浮動小数点数の最後の桁まで一致 しました。

    実データのテストは、Haskell 版と同じ期待値で書き、データが無ければ保留にします。第 8 章の実行は、model/survived.json に学習済みのパイプラインを保存します。

    期待する出力は次のとおりです。

    データ件数: 891（生存 342, 死亡 549）
訓練データ: 712 件, テストデータ: 179 件

    実データでの実測について

    この章は学習データの無い環境で書いたため、上の出力と深さ 2 の値（見つけた生存者が 41 人から 68 人）はまだなでしこ3 版の実装で実測していません。学習データを配置した環境で npx gulp apps:check:nadesiko3 を実行し、保留が消えて通ることを確かめてから、この注記を外します。自作の 20 行のデータでは Python の参照実装と報告が 1 文字も違わないこと、891 行の自作データでは報告と保存したモデルが最後の桁まで一致することを確かめています。891 行の自作データを ML_DATA_DIR で指して ./tools/check.sh を実行すると、落ちるのは実データの値の不一致だけ（2 件）で、検査結果報告の行まで届きました。

    実データの分岐では、期待値の比較のために 第8章実行 を呼びます。これは章を動かしたときと同じ model/survived.json に書くので、テストを始める前に無かったファイルとフォルダだけを後片付けします。学習は決定的なので、もともとあったファイルは同じ中身で上書きされます。

    効果は深さによって変わる¶

    深さによる効果の違い（深さ 2 では見つけた生存者が 41 人から 68 人に増え、テストの正解率は 0.765 から 0.737 に下がる）は、Haskell 版の 8.11 節の表を参照してください。なでしこ3 版では深さ 2 の 2 つの数（41 と 68）をテストに固定しています。重みは「正解率」と「見落としの少なさ」を交換している という読み方は、どの言語版でも同じです。

    突き合わせる相手が 1 つも無いとき、何が正しさを支えるのか¶

    支え 確かめられること
    小さなテスト（74 件、うち保留 3 件） 1 つ 1 つの関数の振る舞い（空欄の扱い・同点の扱い・知らないグループやカテゴリ・壊れたファイル）
    第 3 章の決定木との縮退 重みがすべて 1 なら第 3 章と同じ木。予測は第 3 章の関数をそのまま使う
    自作データと参照実装 20 行と 891 行で、報告と保存したモデルが最後の桁まで一致すること
    ほかの言語版の数値 実データでの正解率・見つけた生存者・架空の乗客の予測（データのある環境で確かめる）

    Haskell 版には「木の形そのものをテストで固定できる」（代数的データ型をそのまま書ける）という支えがありました。なでしこ3 版でも、木は辞書なので {"種別": 「節」, "分割": {...}, "左": ..., "右": ...} とそのまま期待値に書けます。保存したモデルが JSON なので、参照実装とモデルの中身を丸ごと突き合わせられる のは、なでしこ3 版で新しく得た支えです。

    8.12 品質チェック¶

    ./tools/check.sh

    npx gulp apps:check:nadesiko3 で、文法・整形・テスト・テストが最後まで走ったか・関数の網羅の 5 つをまとめて実行します。第 8 章を足したあとの関数の網羅は 98 件中 98 件（直接 68 件、間接 30 件） でした。第 8 章のテストファイルは、学習データが無ければ約 1.3 秒、891 行の自作データを指すと約 3 秒で終わります。

    検査に止められたところ¶

    1. 「{」 が文字列の埋め込みの始まりになる — 辞書と配列を見分ける関数で先頭の文字を 「{」 と比べたら、展開あり文字列で値の埋め込み{...}が対応していません。 で止まりました。『』の文字列で書きます
    2. 「」の中に「」は入れ子にできない — 報告の最後の行で、埋め込みの中に 予測一覧を「, 」で配列結合 と書いて止まりました。いったん変数に入れてから埋め込みます
    3. 読めない が 読 に割られる — 8.10 節のとおりです
    4. 引数を 対象 と名付けると、渡した値が入らない — ラベルの数を数える関数の引数を 対象 にしたら、文法の検査は通るのに、どのラベルも数えられず 0 件になりました。関数の中で 対象 を表示すると空でした。対象 は AJAX受信 などが結果を入れるシステムの変数の名前です。目標値 に変えて直りました。テストの「生存者 0 人中 1 人を発見」という、ありえない数で気づきました
    5. テスト用の関数の助詞を取り違える — テストの中で表を組み立てる (列名一覧と値表から)試験表作成 を「A から B の」で呼んで、未解決の単語があります で止まりました。定義の助詞と呼び出しの助詞は一致させます
    6. 2 億命令の上限 — 8.8 節のとおりです。学習データの無い環境では実データの分岐が動かないので、自作の 891 行のデータを指して動かさなければ気づきませんでした

    4 と 6 は、どちらも文法の検査が何も言わないまま、実行して初めて分かった問題です。4 はテストの期待値で、6 は実データと同じ大きさのデータで捕まえました。小さなデータのテストが通っても、実データと同じ量のデータで一度は動かす 必要があります。

    8.14 まとめ¶

    この章では、タイタニック号の乗客データを題材に、前処理パイプラインとクラスの重みを付けた決定木を、なでしこ3 の TDD ですべて自作しました。なでしこ3 に固有の論点は次のとおりです。

    1. 前処理を「種別」を持つ辞書で表す — 場合分けの最後を必ずエラーにして、知らない種別が素通りしないようにする。漏れはテストで捕まえる
    2. セルは文字列にそろえてから比べる — CSV取得 は数字だけのセルを数値にする。グループやカテゴリは文字列で比べ、空欄は === で判定する
    3. グループのキーは値の配列を JSON にした文字列 — 辞書のキーは文字列だけなので、どんな値でも衝突しない形にする
    4. 配列と辞書は参照で渡る — 前処理は行を複製してから書き換え、新しい表を返す。元の表が変わらないことをテストにする
    5. 足す順をそろえる — 重み付きの不純度は足す順で最後の桁が変わり、同点の扱いを通して木の形に効く。Haskell 版と同じく前から順に足す。参照実装でも Python の sum を使わない
    6. 1 回の実行に 2 億命令の上限がある — 素直な実装は自作の 891 行のデータで上限に届いた。足す順を変えずに、合計をその場で数える形にした
    7. 保存は JSON で簡単、読み込みは形を確かめる — 変数型確認 は辞書と配列を見分けず、JSONデコード は後ろのごみを無視する。形・形式の名前・版・余りを確かめて、壊れたファイルはエラーにする
    8. 名前の落とし穴がさらに 2 つ — 読めない は 読 に割られ、引数の 対象 には値が入らない
