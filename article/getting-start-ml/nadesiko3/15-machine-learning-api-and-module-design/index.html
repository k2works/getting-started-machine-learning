            • 15.1 はじめに
            • 15.2 層を分ける
              • ファイルと依存の向き
              • 置き場の約束を辞書で書く
              • 辞書が保証しないこと
            • 15.3 TODO リストの作成
            • 15.4 要求を読んで検証する
              • JSON の値の種類を見分ける
              • 型が合うかを確かめる
              • 理由を集めて、無ければ値を作る
            • 15.5 置き場の約束をテストで書く
              • 約束のテストを本物と偽物の両方に走らせる
            • 15.6 ドメインとサービス
              • 失敗を結果の辞書で表す
              • 既存のモデルをアダプターで約束に合わせる
              • サービスは要求の形を知らない
            • 15.7 モデルをファイルに保存する
            • 15.8 振り分けと応答
              • 経路の振り分けは表を引くだけ
              • 失敗をステータスコードに変える
              • 応答は辞書、コマンドは JSON の文字列
              • 後ろに続く文字は捕まえられない
              • 標準入出力の入口
            • 15.9 実データで学習したモデルで動かす
              • 学習と保存
              • 予測値はほかの言語版と一致するか
              • 命令の数

    第 15 章: 機械学習 API とモジュール設計¶

    15.1 はじめに¶

    シリーズの最後の章です。ここまでに作ったモデルは、テストと main.nako3 の報告の中でしか使えませんでした。この章では、第 7 章の線形回帰（映画の興行収入）と第 8 章のパイプライン（乗客の生存）を、ほかのプログラムから呼べる 予測の API にします。

    ほかの言語版は、同じ 3 つのエンドポイントを HTTP で公開しています（Haskell 版の第 15 章・Java 版・PHP 版 など）。

    メソッド パス 役割
    GET /health モデルを読み込めるかどうかを返す
    POST /cinema/sales 映画の特徴量から興行収入を予測する
    POST /survived 乗客の特徴量から生存を予測する

    ところが、なでしこ3（nadesiko3go 3.8.8）には HTTP サーバーの命令がありません。そこでこの章では、予測を JSON の標準入出力でやりとりするコマンド として作ります（ADR 015）。要求を {"method", "path", "body"} の JSON で標準入力から受け取り、応答を {"status", "headers", "body"} の JSON で標準出力に返します。

    $ echo '{"method":"GET","path":"/cinema/sales"}' | ./bin/gonako main.nako3 chapter15-api
{"status":405,"headers":{"Allow":"POST"},"body":{"detail":"許していないメソッドです"}}

    HTTP の代わりに JSON の封筒を使うだけで、経路・検証の理由・ステータスコードはほかの言語版の API と同じ約束にそろえます。この章の主題は「API とは約束（入力の検査・出力の形・失敗の返し方）である」ということで、その約束は通信の手段を HTTP から標準入出力に替えても変わらないからです。

    この章でなでしこ3 らしいのは次の 4 点です。

    1. 約束は無名関数の辞書で書く — 型もインターフェースも無いので、置き場もモデルも {"予測": 関数(入力)} のような辞書で表します。偽物の置き場は辞書のリテラル 1 つで作れます
    2. 失敗はエラーではなく結果の辞書で返す — エラー発生 が運べるのは説明の文字列 1 つだけです。422 では理由を並べて返し、503 と 500 では失敗の種類を見分けたいので、{"成否", "値"} か {"成否", "理由一覧"} の辞書で返します
    3. JSON の値の種類は自分で見分ける — 変数型確認 は辞書・配列・NULL をどれも object と答え、無いキーを読むと NULL ではなく undefined が返ります
    4. 関数を名前空間で分けられない — 取り込んだファイルの関数はすべて同じ名前の空間に入ります。層ごとにファイルを分けても、名前はすべて一意にします

    辞書が保証しないこと¶

    辞書が決めるのは キーの名前 だけです。関数の引数の数も、戻り値の形も、「無ければ見つからないを返す」という取り決めも書けません。Haskell 版のレコードは少なくとも型を決めていましたが、なでしこ3 の辞書はそれすら決めません。キーを書き違えても、取り出した値を呼んだ時点で「関数ではない値を呼び出そうとしました。」という実行時エラーになって初めて分かります。

    この取り決めは、15.5 節の 約束のテスト で守ります。型の支えが無いぶん、約束のテストが唯一の支えになります。

    15.6 ドメインとサービス¶

    失敗を結果の辞書で表す¶

    Haskell 版は失敗を直和型（LoadError・PredictError）で表し、ステータスコードへの変換をパターンマッチの網羅で守りました。なでしこ3 には直和型がありません。エラーはあります（エラー発生 と エラー監視）が、運べるのは説明の文字列 1 つだけです。

    そこで、失敗も成功も 結果の辞書 で返すことにしました。読み込みの失敗は種類と名前を持ちます。

    # モデルがまだ保存されていないときの結果。
●(名前の)モデル不在作成とは
    {"成否": 偽, "失敗": 「見つからない」, "名前": 名前}で戻る
ここまで

# ファイルはあるが、モデルとして読めないときの結果。
●(名前の)モデル破損作成とは
    {"成否": 偽, "失敗": 「読めない」, "名前": 名前}で戻る
ここまで

    直和型と違い、「失敗」のキーに書ける値は何も縛られません。「見つからない」 を 「見付からない」 と書き違えても、どこも止まりません。これを捕まえるのも、失敗の種類ごとにステータスコードを確かめるテスト（15.8 節）です。

    15.8 振り分けと応答¶

    経路の振り分けは表を引くだけ¶

    経路は、パスごとに許すメソッドと行き先を持つ辞書の表にしました。

    # 経路の表。パスごとに、許すメソッドと行き先を持つ。
予測経路表 = {"/health": [「GET」, 「ヘルス」], "/cinema/sales": [「POST」, 「売上予測」], "/survived": [「POST」, 「生存予測」]}

# メソッドとパスから行き先を決める。知っているパスに違うメソッドなら、許すメソッドを添える。
●(方法とパスの)予測経路決定とは
    もし、(予測経路表のパスがハッシュキー存在) = 偽ならば
        {"行き先": 「不明」}で戻る
    ここまで
    経路 = 予測経路表[パス]
    もし、方法 !== 経路[0]ならば
        {"行き先": 「許可外」, "許可": 経路[0]}で戻る
    ここまで
    {"行き先": 経路[1]}で戻る
ここまで

    メソッドの比べ方は !== なので、get と小文字で送ると 405 になります。メソッドの文字列をそのまま比べる Haskell 版の振り分けと同じ振る舞いです。

    失敗をステータスコードに変える¶

    # 予測の失敗をステータスコードに変える。
# モデルが見つからないのは一時的な状態なので 503、読めないモデルと予測の失敗は、
# 内部の事情を応答に出さないよう 500 にする。
●(失敗の)予測失敗応答作成とは
    もし、(失敗["失敗"] = 「読込」) かつ (失敗["読込失敗"]["失敗"] = 「見つからない」)ならば
        503と(失敗["読込失敗"]の読込失敗説明)の説明応答作成で戻る
    ここまで
    500と「予測できませんでした」の説明応答作成で戻る
ここまで

    Haskell 版では、失敗の種類を増やしたときにこの関数の節を書き漏らすと、コンパイラが止めました。なでしこ3 では、種類を増やしても何も止まらず、その種類は黙って 500 になります。ステータスコードごとのテスト（200・404・405・422・500・503）を並べて、写し方を固定しました。

    応答は辞書、コマンドは JSON の文字列¶

    ハンドラーは応答を辞書で返します。{"status", "headers", "body"} の辞書をそのまま 一致確認 で比べられます。

    「許していないメソッドは 405 で Allow を添える」で(作り物置き場と「GET」と「/cinema/sales」とNULLで予測要求処理)と{"status": 405, "headers": {"Allow": 「POST」}, "body": {"detail": 「許していないメソッドです」}}が一致確認

    コマンドの層は、要求の文字列を読んでハンドラーに渡し、応答を JSON の文字列にします。要求そのものが読めない（JSON でない・辞書でない・method と path が文字列でない）ときは 400 にしました。HTTP のサーバーが、形の壊れた要求に返すステータスコードです。

    # 要求の JSON の文字列を読み、応答の JSON の文字列を返す。
# 要求そのものが読めなければ（JSON でない・オブジェクトでない・method と path が文字列でない）400 にする。
●(置き場と要求文字列で)予測コマンド処理とは
    要求 = NULL
    エラー監視
        要求 = 要求文字列をJSONデコード
    エラーならば
        要求 = NULL
    ここまで
    応答 = 400と要求外形不正文言の説明応答作成
    もし、(要求の要求値種類) = 「辞書」ならば
        方法 = 要求の「method」を要求列取得
        パス = 要求の「path」を要求列取得
        もし、((方法の要求値種類) = 「文字列」) かつ ((パスの要求値種類) = 「文字列」)ならば
            応答 = 置き場と方法とパスと(要求の「body」を要求列取得)で予測要求処理
        ここまで
    ここまで
    応答をJSONエンコードして戻る
ここまで

    応答のキーは status・headers・body の順に並びます。なでしこ3 の辞書はキーを入れた順を保ち、JSONエンコード もその順で書くからです（第 2 章）。Haskell 版の aeson はキーを並べ替えたので、応答の並びを約束にできるのはなでしこ3 版のほうでした。

    後ろに続く文字は捕まえられない¶

    保存したモデルと違い、送られてきた要求は元の文字列の形が分かりません。空白や改行やキーの順は送り手しだいなので、JSON に戻して比べる手が使えないのです。そのため {"method": "GET", "path": "/health"} おまけ のような要求は、後ろの おまけ を無視して 200 を返します。直せない限界として、そのとおりの振る舞いをテストに書いて残しました。

    # JSONデコード は先頭の値を 1 つ読んだところで止まり、後ろに続く文字を黙って無視する。
# 送られてきた要求は元の文字列が分からないので、第 8 章のモデルの読み込みのように JSON に戻して比べられない。
「要求の後ろに続く文字は見逃す（JSONデコード の限界）」で(作り物置き場と『{"method": "GET", "path": "/health"} おまけ』で予測コマンド処理)と『{"status":200,"headers":{},"body":{"status":"ok","models":{"cinema":true,"survived":true}}}』が一致確認

    応答 = (フォルダのファイル置き場作成)と入力で予測コマンド処理
    応答 & 改行で戻る
ここまで

    Haskell 版は、見本の映画（sns1=200, sns2=500, actor=3000, original=1）の予測値を次のように記録しています。

    PHP 7730.457421687019

    15.11 まとめ¶

    この章では、第 7・8 章のモデルを、JSON の標準入出力でやりとりする予測のコマンドにしました。なでしこ3 に固有の論点は次のとおりです。

    1. HTTP が無くても API の約束は書ける — 要求と応答を JSON の封筒にし、経路・検証の理由・ステータスコードをほかの言語版とそろえた。通信の手段は約束の外にある
    2. 約束は無名関数の辞書で書き、テストで守る — 辞書が決めるのはキーの名前だけで、引数も戻り値も縛れない。約束のテストを本物と偽物の両方に走らせた
    3. 失敗はエラーではなく結果の辞書で返す — エラーは説明の文字列しか運べない。理由の一覧と失敗の種類を持たせるために辞書にした。直和型のような網羅の確認は無いので、ステータスコードごとにテストを並べた
    4. JSON の値の種類は自分で見分ける — 辞書・配列・NULL はどれも object、無いキーは undefined。JSON に戻した先頭の文字と ハッシュキー存在 で見分けた
    5. 比べた結果を返すときはかっこで囲む — 種類 = 「数値」で戻る は代入と読まれ、実行時に止まる。lint は通る
    6. 命令の書式は doc で確かめる — (値の切捨) は「を」で呼ぶ命令を「の」で呼んだため undefined になり、どの数も整数でないと判定した。lint は通る
    7. 取り込みは名前空間を作らない — 層ごとにファイルを分けても、関数の名前はすべて一意にする

    15.12 なでしこ3 版のまとめ¶

    番外編を 15 章書き終えたので、なでしこ3 版で分かったことをまとめます。

    なでしこ3 版は、14 の言語版のあとに 日本語で書く言語 として加えました（ADR 015）。対比の軸は 2 つでした。1 つは Python 版 で、同じ手順を英語の識別子と日本語の文で書き比べること。もう 1 つは Haskell 版・Go 版 で、機械学習のライブラリが無いことです。

    日本語で書けることと、日本語の名前の難しさ¶

    機械学習の用語はそのままコードになりました。(特徴量一覧と正解一覧を列名一覧と深さ上限で)乗客重み付き部分木学習 のように、関数の定義が手順の説明として読めます。

    一方で、名前の付け方は 15 章を通していちばん多く踏んだ落とし穴 でした。

    • 助詞とひらがなは名前を割る（第 1 章）。ルールで判定 は「ルール」の定義に、きのこ派の年代 は「き」「の」「こ派」に割られます
    • 漢字に挟まれた送り仮名は名前から落ちる（第 9 章）。外れ値試験 と 外値試験 は同じ関数です
    • 組み込みの名前と重なると、分かりにくい形で壊れる。終了 はプロセスを終了コード 0 で黙って終わらせ（第 3 章）、対象 は引数に値が入らず（第 8 章）、次 は「『ここまで』がありません」になり（第 3 章）、巡回・違反 は構文の語と読まれ（第 12 章）、表示 は代入できません（この章）
    • 呼び方の違いは lint を通る。定義と違う助詞で呼ぶと直前の値が入り（第 13 章）、命令を「の」で呼ぶと undefined になり（この章）、名前を付けた関数を値の位置に書くとその場で呼ばれます（第 11 章）

    日本語で書けることは、英語の識別子より自由に書けることを意味しませんでした。助詞が文法の役割を持つぶん、名前に使える語は英語より狭い のです。

    守りはテストだけ¶

    なでしこ3 版には、型の検査もカバレッジもありませんでした。lint は未定義の名前を半分しか捕まえません。残る守りはテストだけです。

    そのテストの道具も自作しました。テスティングフレームワークが無く、ASSERT等 は最初の失敗で止まるので、失敗を数えて最後に報告するテスト補助を作りました（第 1 章）。カバレッジの代わりに、テストから届かない関数を見つける「関数の網羅」を作りました（第 5 章）。そして、テストが空振りしていないことを、実装や検査をわざと壊して落ちることで確かめ続けました（第 1・6・7・10〜14 章とこの章）。

    テスト補助そのものにも不具合がありました。近似確認 は差が NaN のとき合格にしていて、第 7 章で見つけて直しました。守りの道具も、守られる側のコードと同じようにテストする 必要があります。

    命令の上限という新しい制約¶

    gonako は 1 回の実行で 2 億命令を超えると止まります（第 3 章）。素朴に書いた第 8・10・14 章は上限に届き、計算の結果を 1 ビットも変えずに書き方を変えて 収めました。命令を数える処理系を作り、足す順と同点の扱いを守りながら、繰り返しを Go で書かれた命令に置き換え、同じ計算を数え上げに直しました。速い書き方を入れたときは、素朴な書き方をテストに残して丸ごと比べました（第 14 章）。

    ほかの 14 の言語版では、性能は「速いか遅いか」の問題でした。なでしこ3 版では「動くか止まるか」の問題になりました。

    自作の正しさを何で支えたか¶

    なでしこ3 には機械学習のライブラリも行列の命令もなく、線形代数（連立一次方程式と固有値分解）も自作しました（第 7・13 章）。突き合わせる相手のライブラリは 1 つもありません。

    代わりに支えたのは、次の 3 つでした。

    1. ほかの言語版の数値 — 第 2 章で java.util.Random と同じ線形合同法を float64 だけで自作し、シード 0 の並びがほかの言語版と一致することを確かめました。この土台の上で、各章の期待値をほかの言語版の値にしました
    2. Python の参照実装 — 同じ規則・同じ演算順で書いた参照実装と、実データと同じ形の架空のデータで、報告を 1 文字ずつ、数値を最後の桁まで突き合わせました
    3. 満たすべき性質 — 固有値分解の A v = λ v（第 13 章）、alpha 0 のリッジ回帰と線形回帰の一致と KKT 条件（第 12 章）、交差検証で全行がちょうど 1 度テストされること（第 11 章）

    ただし、実データ（配布データ）での実測は、どの章もまだ行っていません。学習データの無い環境で書いたためです。記事に載せた実データの数値は、ほかの言語版の値を「期待する出力」として示したもので、各章の注記に書いたとおり、学習データを置いた環境で確かめるまで未確認です。CI は main への pull request で初めて走り、学習データの無いランナーで、実データのテストを保留にしたまますべての検査が通りました。

    最後に¶

    第 1 章の「20 代ならきのこ派」という手書きのルールから始めて、この章で学習したモデルを JSON で届けるところまで来ました。

    なでしこ3 版で効いたのは、約束をテストに書き、そのテストが本当に落ちることを確かめる という、どの言語版でも同じ規律でした。型が無く、lint が半分しか捕まえず、名前が文法と衝突する言語では、その規律が省けませんでした。

    変更を楽に安全にできること。 日本語で書けることは読みやすさを与えてくれましたが、変更を安全にしてくれたのはテストでした。それが、14 の言語版のあとに日本語の言語で書いて分かったことです。

    なでしこ3 版のほかの章は なでしこ3 版のトップ から辿れます。
