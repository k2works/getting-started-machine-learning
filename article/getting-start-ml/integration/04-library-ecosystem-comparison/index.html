    第 4 章: ライブラリのエコシステムの比較¶

    4.1 突き合わせの目的¶

    各言語版の第 3〜14 章では、アルゴリズムを TDD で自作したあと、その言語の機械学習ライブラリに同じデータを渡して結果を突き合わせました。目的は 2 つです。

    • 自作が正しいことの裏付け: 仕組みの違う実装どうしで結果が一致すれば、自作が妥当に動いていると言える
    • ライブラリの振る舞いを知る: 既定値や定義の違いは、ドキュメントを読むだけでは見落とす。学習用テストで確かめてから使う

    4.3 「ライブラリにある」と「そのまま比べられる」は別¶

    第 3 波で新しく出てきた論点です。ライブラリに手法があっても、自作と同じ条件に設定できるとは限りません。

    PHP の Rubix\ML\Classifiers\ClassificationTree は決定木を持っています。しかし既定のままでは、次の理由で自作と比べられませんでした。

    • CART::split() が使う列を array_rand で毎回選ぶ（maxFeatures の既定は round(sqrt(n))）
    • 連続値の候補を分位点で丸める（maxBins の既定は 1 + round(log2(m))）
    • 葉の大きさと不純度の下限に既定値がある

    maxLeafSize: 1・minPurityIncrease: 0.0・maxFeatures: 列数・maxBins: 大きい値 の 4 つを明示して初めて、深さ 1〜5 で完全に一致しました。Elixir 版がこの章で「突き合わせる相手がいない」という仕事をしたところで、PHP 版には「相手はいるが、そろえる」という別の仕事が現れたということです。

    同じことが Ruby でも起きました。Rumale::LinearModel::LinearRegression は、Numo::Linalg が読み込まれていないと L-BFGS（tol の既定は 1e-4）で解き、solver: "svd" を指定しても黙って L-BFGS に落ちます。既定のままでは切片が 0.0044（自作は 6035.99）、テストの決定係数が −1.246 になり、例外も警告も出ません。tol: 1e-10 にして初めて、自作との差が 3.5e-5 以内になります。

    そろえきれない場合もあります。PHP 版で、深さを制限しないときだけ 0.9333 対 0.9111 と食い違った原因は境界の取り方でした——自作は隣り合う値の中点、Rubix ML はデータに実在する値を使います。これは引数で変えられません。

    定義や尺度が違う¶

    標準偏差を「件数で割るか、件数 − 1 で割るか」は、シリーズ全体でいちばん多く踏んだ落とし穴です。縦持ちで整理します。

    n−1（標本標準偏差） pandas の std()、Tribuo の MeanStdDevTransformation（Kotlin・Java・Scala・Clojure）、ml-matrix の standardDeviation、gonum の stat.StdDev、Rumale の StandardScaler、statistics の stdDev

    • Ruby の Rumale だけが、第 3 波で n−1 側でした。 Scholar・Rubix ML は n 側なので、同じ第 3 波の中で分かれています。ライブラリの癖は言語の性質ではないことが、ここでも出ています

    Elixir Nx.LinAlg.eigh 対称でない行列を黙って受ける（上三角だけを使い、例外も警告も出ない）。固有値は降順、固有ベクトルは列

    Ruby Rumale の confusion_matrix 行が正解・列が予測で、ラベルの昇順に並ぶ。Precision・Recall・FScore は既定（average: "binary"）で y_true の最大のラベルを陽性とみなす
    Haskell hmatrix の trustSym 対称かを確かめず上三角だけを見る。Elixir 版の Nx.LinAlg.eigh と同じ落とし穴（Haskell 版は m /= transpose m で自分から確かめた）

    同数・境界・余りの扱いが違う¶

    言語 ライブラリ 見つかったこと
    Kotlin Tribuo の CART 多数決が同数の葉のラベルの選び方と、同じ不純度の分割候補の選び方が自作と違う
    TypeScript ml-cart 境界ちょうどの値を右に進める。多数決が同数なら訓練データ全体で先に現れたラベルを選ぶ
    TypeScript ml-cross-validation 余りの行が分割数以上だと、行を捨てる
    TypeScript ml-confusion-matrix 正例を一度も予測しないと、適合率が NaN になる
    Rust linfa-trees の find_modal_class HashMap を走査するので、葉のラベルが同数のときの選び方が順に依存しうる
    Ruby Rumale の決定木 節ごとに特徴量を Array#sample でランダムな順に並べるので、同じ不純度の分割が並ぶと自作と違う分割を選ぶ
    PHP Rubix ML の ClassificationTree 分割の境界がデータに実在する値（自作は隣り合う値の中点）。深さを制限しないときだけ食い違った
    PHP Rubix ML の KMostFrequent arsort なので、同点なら先に現れたほうが残る

    「K 分割の余りをどうするか」は、3 通りに分かれました。

    余りの扱い ライブラリ
    先頭の分割に配る 自作（全 14 言語）、Tribuo、Rumale の KFold
    捨てる Scholar の ModelSelection.k_fold_split/2、Rubix ML の Labeled::fold()
    分割数以上なら捨てる ml-cross-validation（TypeScript）

    Scholar と Rubix ML は、891 件を 5 分割すると 178 件 × 5 になり、1 件がどの分割でもテストされません。別々に書かれた 2 つのライブラリが、まったく同じ振る舞いをしていました。自作は 179, 178, 178, 178, 178 で全行をちょうど 1 度テストします。

    Ruby は逆に、行の分け方まで一致しました。 Rumale の KFold の shuffle: true は、第 2 章の shuffle と同じ Random.new(seed) と Array#shuffle を使うので、891 件の 5 分割が行単位で自作と一致します。

    決定的でない¶

    第 3 波で、この節がいちばん大きくなりました。 「同じ入力に同じ出力」が成り立たないライブラリは、linfa-trees だけではありませんでした。

    言語 ライブラリ 見つかったこと
    Rust linfa-trees 同じデータ・同じ深さでも、実行ごとにテストの正解率が 0.788〜0.810 で揺れる（第 8 章の Survived.csv。ダミー変数で同じ不純度の分割候補が並ぶため。iris では揺れない）
    PHP Rubix ML の ClassificationTree array_rand で列を選び、シードを渡す口が無い。 既定のまま 5 回走らせて 0.8889, 0.8889, 0.8889, 0.8889, 0.8222 と揺れた
    PHP Rubix ML の RandomForest・SoftmaxClassifier モデルがシードを受け取らず、大域の mt_rand から引く。 種を付けないと実行のたびに正解率が変わる（softmax で 0.4889〜0.7556）
    PHP Rubix ML の KFold::test() 内部で randomize() を呼ぶがシードを渡す口が無い。5 回で 0.7718〜0.7819 と揺れた
    Ruby Rumale のモデル全般 random_seed を省くと既定値が srand になり、モデルを作るだけでプロセス全体の乱数の種が入れ替わる。 KFold は shuffle: false でもシードを渡す必要がある
    Elixir Scholar の KMeans :key を渡さないと System.system_time() で鍵を作るので、結果が毎回変わる

    PHP 版では、同じ問題に 2 つの章が別の手で対処しました。 第 3 章は引数を明示してくじ引き自体を起こさない（maxFeatures を列数にすれば array_rand の結果に依存しない）、第 10 章は大域の mt_rand に種を付ける。シードを渡す口が無い以上、外から固定するか、乱数が効かない設定にするかの二択になります。

    第 2 波で「自作のほうが再現性が高いという逆転」が linfa で起きたことを書きました。第 3 波では、それが例外ではないと分かりました。 ライブラリは「自分で書くより正しい」とは限らず、「自分で書くより再現する」とも限りません。

    使えない・手法が無い¶

    言語 ライブラリ 見つかったこと
    Kotlin・Java・Scala・Clojure Tribuo PCA のモジュールが無い。K-means は初期中心を渡せない
    F# ML.NET 単一の決定木（CART）の学習器が無い。K-means は初期中心を渡せない
    F# FSharp.Stats 0.6.0 リッジ回帰が、どの大きさの罰則の行列でも次元が合わない例外を投げる
    TypeScript ml.js 系 回帰の評価指標が無い。featureImportance() は型定義に無い
    Go gonum 決定木・ランダムフォレスト・K-means・ロジスティック回帰・正則化付き回帰が無い
    Go gonum の stat.ROC 入力が昇順でないと error ではなくパニックする。AUC は返さない
    Rust linfa・ndarray ランダムフォレスト・欠損値の補完・ダミー変数化が無い。連立方程式を解く関数が無い
    Ruby Rumale・Numo PCA の寄与率が無い。欠損値の補完・基準列を落とすダミー変数化・クラスの重みが無い。Numo に連立方程式を解く関数が無い
    Elixir Scholar 決定木・ランダムフォレスト・ラッソが無い。 SimpleImputer はグループ別の統計量を持てず、OneHotEncoder は最初のカテゴリを落とせない
    PHP Rubix ML 素の線形回帰・ラッソ・ROC 曲線・AUC が無い。 LogisticRegression は 2 クラス専用（多クラスは SoftmaxClassifier）。PrincipalComponentAnalysis が公開しているのは lossiness() と transform() だけで、固有ベクトルも平均も寄与率も取れない
    PHP MathPHP 実データで落ちた。 Eigenvalue::jacobiMethod() が返したばかりの固有値を同じ行列とともに Eigenvector::eigenvectors() に渡すと BadDataException（掃き出し法で零空間を探す実装が 15×15 の浮動小数点に耐えない）
    Haskell — 機械学習のライブラリが無い（hlearn は保守が止まっている）。決定木・ランダムフォレスト・ロジスティック回帰・K-means・評価指標・前処理はすべて自作

    「無いものをどう埋めたか」も、版によって違いました。

    • PHP は、素の線形回帰が無いところを Ridge(0.0) の縮退で代用しました。正則化を 0 にしたリッジが最小二乗にあたることを、自作と突き合わせて確かめています
    • PHP の第 13 章は、公開されていない値を外から復元しました。主成分は transform() が線形変換であることを使って「平均＋単位ベクトル」を通し、寄与率は次元数を 1 ずつ増やして 1 - lossiness() の差分を取ります。リフレクションを使わず、内部の名前にも依存しません
    • Haskell の第 13 章は、hmatrix の eigSH（DSYEV）が 15×15 の実データに耐えました。PHP 版で MathPHP の固有ベクトルが落ちた場所を、そのまま通り抜けています

    4.5 C ライブラリへの依存——確認すべきことが 3 段ある¶

    第 3 波の Haskell で初めて出てきた論点です。 ネイティブのライブラリに依存すると、「入るかどうか」だけでは足りません。

    hmatrix は BLAS/LAPACK を要求します。確認は 3 段ありました。

    1. ビルドが通るか。 素の Nix 環境では configure が Missing (or bad) C libraries: blas, lapack で止まります。ここを通っただけで採用を決めたのが、最初の誤りでした
    2. 呼び出しが通るか。 nixpkgs の openblas は既定が blas64 = true（ILP64。整数引数が 64 ビット）で、32 ビット整数で呼ぶ hmatrix と ABI が噛み合いません。 ビルドは成功するのに、2×2 の連立方程式すら解けませんでした（linearSolve が Nothing を返し、<\> は code -7、pinv は code -2）。blas と lapack（isILP64 = false）に差し替えて解決しています。2×2 の DGESV で「行列の次数が不正」と言われたら、数値の問題ではなく ABI の不一致を疑う、という診断がここで得られました
    3. 環境を変えたあと作り直されるか。 環境定義を直しても、cabal の store に残った成果物は作り直されません。LIBRARY_PATH は環境ごとに変わるのに、cabal はそれをパッケージのハッシュに含めないので、ILP64 の BLAS にリンク済みのものが使われ続けます。store の該当エントリを退避してから作り直す必要がありました

    Elixir 版が EXLA（巨大な XLA のバイナリ）を避けたのとは、判断が逆になっています。BLAS/LAPACK は数値計算の標準的な土台で Nix でも軽く入るため、依存を受け入れました。その代わりに、「ライブラリがビルドできた」は「使える」ではないという確認の段が 2 つ増えています。

    似た形は第 3 波でもう 2 回起きました。PHP の素の Nix 環境にはカバレッジドライバ（xdebug も pcov も）が無く、php.withExtensions で pcov を足す必要がありました。Clojure の環境には clj-kondo も cljfmt も入っておらず、Haskell の環境には fourmolu も hlint もありませんでした。道具立てが環境に足りないことは、第 3 波では例外ではなく既定でした。

    4.6 同じ計算を違う入れ物で渡すと、精度が変わる¶

    第 7 章の線形回帰で、3 つの版が「SVD で解いた」と言いながら 3 通りの結果になりました。

    版 ライブラリ 解き方 結果
    Elixir Scholar の LinearRegression Nx.LinAlg.pinv（SVD） 最小二乗解に届かない。 特異値 [12988, 2648, 1589, 4.28] のデータで、残差平方和が自作 11083165.68 < Scholar 14073810.01。列を標準化してから渡すと有効数字 4 桁までそろう
    PHP Rubix ML の Ridge 正規方程式を inverse() で解く（自作は LU 分解） 12〜13 桁まで一致した（切片 6114.5955056944 対 6114.5955056945）
    Haskell hmatrix の <\>（DGELSS） 計画行列を渡すと SVD、正規方程式を渡しても同じ関数 計画行列なら 12 桁、正規方程式なら 9 桁（6114.5955055106010）

    Haskell 版は、この対照を 1 つのライブラリの中で見せました。 同じ実データを 4 通り（自作のガウス・ジョルダン法／<\> に計画行列／linearSolveLS に計画行列／<\> に正規方程式）で解くと、最初の 3 つは 12 桁まで一致し、最後だけが 9 桁に落ちます。XᵀX を作ると条件数が 2 乗になるという教科書どおりのことが、同じ関数に別の入れ物で渡しただけで出ました。

    面白いのは、自作も正規方程式を解いているのに 12 桁一致していることです。違いは部分ピボット選択つきの消去法と DGELSS（特異値の打ち切りあり）で、残差平方和は 4 つとも下 2 桁しか違いません。どれも最小二乗解の底にはいて、底が平らなので係数のほうが先にぶれる、というのが答えでした。

    Elixir 版が「SVD のほうが数値的に安定である」という一般論に裏切られ、PHP 版が「正規方程式は条件数が悪くなる」という一般論に裏切られています。アルゴリズムの理論的な安定性より、その実装の精度のほうが効く場合があるということです。

    4.7 ライブラリが無いことが、安全な設計を強制した例¶

    第 3 波では、モデルの保存・復元でも版ごとに事情が分かれました。

    版 保存の方法 用心
    Ruby Marshal RuboCop の Security/MarshalLoad を理由つきで 1 行だけ無効にした
    Clojure EDN（pr-str／read-string） 学習済みパイプラインがマップ・ベクタ・キーワードだけなので、値として = で比べられる
    Elixir :erlang.term_to_binary 復元には :safe を渡す
    PHP serialize unserialize() に allowed_classes は必須（既定でどんなクラスでも作る）。しかも unserialize() も mkdir() も失敗を例外ではなく警告で知らせる
    Haskell Data.Binary 用心が要らなかった

    Haskell で用心が要らなかったのは、ライブラリが足りなかったからです。 binary に Text の Binary インスタンスが無く、孤児インスタンスを避けて保存の形式を手書きすることになりました。その結果、「壊れたファイルから任意のものが作られない」という性質が設計に組み込まれました。PHP の allowed_classes・Elixir の :safe にあたる用心が、そもそも要らなくなっています。

    （ただし別の注意は増えました。decodeOrFail は「途中まで読めたら成功」なので、余りが空かまで見る必要があります。）

    往復の精度も分かれました。 Clojure の EDN と Elixir の :erlang.term_to_binary は Double を往復しても桁が落ちず、PHP の serialize も serialize_precision の既定 -1 が最短往復表記を選ぶので、実データでも 1 ビット一致します。

    4.8 エコシステムの成熟度と、自作の意味¶

    14 言語を比べると、ライブラリが成熟しているほど「一致」が増え、成熟していないほど「近似」「比較」「省略」が増えました。

    言語 一致した章 近似・比較・省略の主な理由
    Python 第 3・7・9・11・12・13・14 章（第 10 章のロジスティック回帰も） 乱数の使い方が違う（ランダムフォレスト）
    Kotlin・Java・Scala・Clojure 第 7・11 章 同数・境界の扱い、不偏標準偏差、罰則の尺度、手法が無い（PCA）、初期中心を渡せない（いずれも Tribuo の性質）
    TypeScript 第 7・11・13・14 章 同数・境界の扱い、罰則の尺度、切片が無い
    C#・F# 第 7・9・11・13・14 章（F#） 単一の決定木が無い、リッジ回帰が使えない、初期中心を渡せない（ML.NET の性質）
    Go 第 7・11・13 章（いずれも一部） 手法そのものが無い章が 5 つ
    Rust 第 7・9・10・11・13 章 既定の枝刈りと正則化、目的関数の流儀、k-means++、ライブラリ側が非決定的
    Ruby 第 7・10・11 章（ラッソも） 既定の解き方、n−1 の標準偏差、切片も正則化する、PCA の寄与率が無い、K-means に SSE が無い
    Elixir 第 9・10・11・13 章 決定木・森・ラッソが無い、SVD が最小二乗解に届かない、指標が f32 に落ちる
    PHP 第 7・9・12・13 章 既定値をそろえる手間、F 値の定義、ROC が無い、シードを渡す口が無い
    Haskell 第 7・9・12・13 章 機械学習のライブラリが無く、線形代数と統計だけが相手

    同じライブラリを使う言語は、同じ結果になりました。 Java・Scala・Kotlin・Clojure（Tribuo）と C#・F#（ML.NET）は、突き合わせの結果も見つかった癖もほぼ同じです。第 3 波で Clojure が同じ Tribuo 4.3.2 を同じ JDK 21 で呼んだ結果、自作と CART の相違件数（深さ 1〜10 で 0,0,0,0,2,0,0,0,1,0）まで Java 版・Scala 版と一致しました。ライブラリの癖は言語の性質ではなく、ライブラリの性質だということが、4 言語で確かめられたことになります。

    ただし、「一致しない」ことは失敗ではありません。一致しなかった原因を学習用テストで突き止めたことで、ライブラリの定義（同数の扱い・罰則の尺度・F 値の平均の取り方）を正確に理解できました。ライブラリが無い部分は、自作が最終実装になります。

    そして、ライブラリが無い版でも正しさは支えられました。 Haskell 版の第 11 章は、突き合わせる相手が 1 つも無い状態で、「値の分かっている入力」「満たすべき性質」「ほかの言語版の数値」の 3 つで正しさを示しています。ほかの言語版の数値が突き合わせの相手になるのは、14 言語で同じ題材を書いたシリーズならではの支え方です。第 3 波の 3 言語（Elixir・PHP・Haskell）が乱数生成器を自作して JVM の言語版と並びをそろえたのは、まさにこのためでした。

    4.9 まとめ¶

    1. 章ごとの突き合わせ — 第 7 章（線形回帰）は 14 言語すべてで、第 11 章（評価指標）は相手のいる 13 言語すべてで一致した。ほかの章は、ライブラリの成熟度によって一致・近似・比較・省略に分かれた
    2. 置き換えの範囲は言語で大きく違う — PHP（Rubix ML）はほぼ全章、Elixir（Scholar）は決定木が無いので狭く、Haskell は機械学習のライブラリが無く線形代数だけ。第 11 章は「突き合わせの節が存在しない」シリーズ唯一の章になった
    3. 「ある」と「そのまま比べられる」は別 — Rubix ML の決定木は 4 つの引数を明示して初めて比べられ、Rumale の線形回帰は tol を下げるまで切片が 0.0044 だった。相手がいることは、そろえる仕事が要ることでもある
    4. 既定値を疑う — 正則化・エポック数・学習率・葉の最小件数・fixZero・min_impurity_decrease・Nx の f32・Ridge の l2Penalty など、「何もしない」と思った既定値が結果を変えた
    5. 定義をそろえる — 標準偏差の割り方は 11 のライブラリで割れた。statistics のように 1 つのライブラリが両方を持つこともあり、名前から推測すると間違える。K 分割の余りは「配る／捨てる」で分かれ、Scholar と Rubix ML が同じ「捨てる」だった
    6. 決定的とは限らない — linfa-trees・Rubix ML の 3 つのクラス・Rumale のモデル・Scholar の KMeans が、種を渡さないと揺れた。シードを渡す口が無い場合は、くじ引きを起こさない設定にするか、大域に種を付けるしかない
    7. C ライブラリへの依存は 3 段で確認する — ビルドが通るか、呼び出しが通るか（ABI の整数幅）、環境を変えたあと作り直されるか。ビルドが通っただけでは使えない
    8. 同じ計算でも入れ物で精度が変わる — 「SVD で解いた」が 3 つの版で 3 通りになった。アルゴリズムの理論的な安定性より、その実装の精度のほうが効く場合がある
    9. 癖はライブラリの性質 — 同じ Tribuo を使う 4 言語（Java・Kotlin・Scala・Clojure）は、相違件数まで同じだった
    10. 一致しないことも学び — 原因を学習用テストで突き止め、ライブラリの定義を理解した。手法が無い部分は自作を最終実装にし、ほかの言語版の数値を突き合わせの相手にした

    次の章では、目的に応じた読み方を案内します。
